## What the build delivers

A person explicitly selects a device debate on a supported chain. The session and seats debate the physical design, its interfaces, how it would be made, what evidence supports it, and how a person could check it. THC produces its usual plan, debate record and milestone handoff, plus an optional illustrated overview tied to the draft it depicts. Software stays the default. Hardware size is unrestricted. A large project can yield a system-level plan with named subsystem debates, interfaces and outstanding decisions. Each further run has its own authorization and limits.

Keep the current proposal, debate, judging, revision and acceptance machinery. The handling session writes the plan and draws the overview. The base feature adds no seat, round or paid call. Actual cost can change with text length and how long the debate lasts. Retain BYOK, MIT, reasoning effort, spend controls, existing provider restrictions and the owner’s control of releases. This workstream changes no roster.

The hard part is preserving meaning between outputs. A supplied estimate stays an estimate in the plan, on the sheet and in the handoff. A proposed physical check stays planned until a person reports an observation. Agreement records what the judges decided about the *plan*. A simulation, calculation, illustration or mock run supplies no physical test result.

## Evidence, criteria and physical checks

The request supplies a “Reference data” section with one fenced extract per source. Place `REF-<positive integer>: <source and location>` immediately above the fence or on the first line inside it. Measurements identify who, when and with what instrument. Prices carry dates. “Available instruments” is a separate optional list, one exact name per line. Device fence output and hand-written blocks must round-trip through the same reader. The command may retain the existing “Source, fenced verbatim” section heading as an equivalent machine-generated location. Give it a wholly device-specific body. Preserve per-file size, truncation, redaction and path rules. Supply **text extracts** of documents and diagrams. A filename is not an extract.

Use `parseFences` to index complete blocks with a nonblank source label and payload. A REF in ordinary prose, in a nested example, on a blank/incomplete fence, or in a quoted instruction cannot create a second source. Conflicting inside/outside labels and duplicate IDs are ambiguous: leave those IDs unusable, explain which to renumber, and treat dependent claims as unsupported. New fences allocate above the highest already used positive ID and preserve software fence output and existing content. On mixed/repeated invocations keep one heading, retain existing blocks, and never silently rewrite an authored source. If an existing software header would give conflicting device instructions, explain how to use a distinct reference section before appending there.

For device requests, warn about unfenced PDF, PNG, JPG/JPEG, SVG, DXF, DWG, STEP/STP, STL, IGES, BRD, SCH and GBR mentions unless the person marked them mention-only through the existing mechanism. A source label naming the document for an actual reference block counts as a supplied extract of that document only. Match names as paths or bounded tokens and ignore fences/examples when scanning prose. Preserve the existing code/text artifact checks. Warn when no usable REF block exists. Warn when the whole request including fences exceeds half the smallest known seat input window, using the existing token estimator and effective roster. Unknown windows offer no assurance of fit. At the half-window boundary use a strict greater-than comparison, estimate the same task text the seat would receive and never perform a provider lookup for missing window sizes. These are base-mode notices pending M2.

| Claim or objection | Rule |
| --- | --- |
| Stated | Cite the request for a user requirement and REF or an approved excerpt for sourced values. Preserve the source’s own status and units, including “estimated”, tolerance or range. A catalog rating and a measurement on this particular item are different claims. |
| Worked out | Show inputs, units, calculation and source IDs. Use `[CHECKED: inferred from REF-1, REF-2: <calculation>]` only when every input is sourced. A calculation from an estimate stays an estimate. With an uncertain input use `[UNVERIFIED: <what would settle it>; <calculation>]`. |
| Missing or disputed | Use a placeholder with its resolving action. Preserve the existing CHECKED, UNVERIFIED, ABSENT and DISPUTED grammar and the existing restriction on who can write DISPUTED. Keep unknown values out of pass thresholds except as explicit blockers. |
| Judge quote | A physical assertion needs source evidence. Search **each** supplied reference block and **each** shown excerpt independently using the existing case-sensitive, whitespace-normalized quote comparison. Resolve a source hit as `verified`, excerpt as `in_excerpt` with ID, a draft-only hit as an anchor with no source-verification status, and a supplied quote found nowhere as `unverified`. A draft-only quote can show what the plan said. If there is no supporting source for the physical assertion, ask a question or mark it UNVERIFIED. Preserve every objection, its ID, spans and verdict. No invented classifier for arbitrary unquoted prose is required. |
| Marker finding | Check direct and inferred REF citations against that request’s unique block index. Report `ref_unknown` for each distinct missing/ambiguous ID per marker. Continue checking any excerpt IDs in the same marker. A hit establishes provenance only. Keep findings informational. |

The handling session can add evidence through the existing project-file excerpt channel. A reference extract starts with its source. A calculation starts with “Calculation by the handling session” and names the calculation. It can support a derived value. Treat the first line as the first line of the **shown extract**, which may start at any source-file offset. Only keep a source/calculation designation if the approved bytes include the actual designation. A cut to shown lines 3–5 may include shown line 1 and the hidden-lines marker for line 2 **only when that exact preview is what the person approves**. Represent the result with the existing range, hide and original file offsets. Reject a hide of the mandatory label. Offer withholding the entire excerpt. Never restore text from outside the shown or approved range. Apply the same normalization before display, validation, recording and replay. Keep the existing scan and approval binding. Generic excerpts that lack a source label remain ordinary context.

**Criteria lock.** For a device run, include the canonical hazard criterion W6c exactly once before criteria are locked and shown to any proposer or judge. Ask the criteria writer for that exact criterion, regardless of `decisions`. After the existing response guards, check what actually came back. If a usable generated list omits it, append W6c locally and disclose the addition. Do the same for chain criteria, `--criteria`, and `--from-run`/`from_run`, including a source report with the device label. Preserve original order, text, kind and checks. Use a string for an untyped list and the existing judgement object shape for a typed list. An existing canonical row already counts. Preserve a user's original duplicate rows and flag the input for correction before lock instead of deleting or renumbering accepted obligations. Validate the complete list against existing constraints, including applicable size limits. If addition cannot fit, give an actionable pre-lock error; never evict another criterion or make a paid retry for this repair. Persist the accepted device list and kinds using existing run evidence where possible. Replay that list on resume even if a source file changes. The report, handoff and notices must agree on the IDs.

**Proportional detail.** Record who will build, the intended use and environment, available instruments, unknowns and dependencies, and whether the intended use is personal or commercial. For a larger system name subsystem owners or outstanding ownership, interfaces and boundary assumptions. Give each named hazard its source, consequence, control and a planned verification. For functions implicated by those hazards use rows for function, failure mode, cause, effect, detection, compensation, severity in words and basis. Detection and compensation must refer to an actual plan section or be explicitly missing. State an inferred failure mode as UNVERIFIED and name what would settle it. For a simple case, a short supported statement can explain why no row applies. Judges can flag a foreseeable mechanism as a question when evidence is missing. They must not let speculation acquire the status of a measured fact.

## Blueprint transaction

The session derives the overview from the plan it just wrote. First build the table. Include one row per part and interface with its plan section, and one row for each depicted value with its unit, kind and plan section. Mark stated, worked-out and unspecified values with text and line style as well as any color. Preserve estimates. Draw only from the table. The drawing script runs in the handling session’s own environment. THC stores its output as data. If the drawing exposes a gap, fix or mark the gap in the written plan before submitting the matching table. The handoff names the written plan as authoritative.

Request the sheet on external `build`, on each `revise-<n>` that changes the accepted body, and on a `dispute` rewrite. An unchanged revision can reuse the last matching sheet. A handed-in draft may have no writer stage. A skipped dispute has no sheet submission. The base design permits a run to finish without a sheet and records that fact. An invalid *supplied* sheet is recoverable at the waiting stage.

**Input**, optional on those stages only. Omit `code` when there is no script. Supply exactly one of `picture` and a nonblank single-line `no_picture`. The illustration can be PNG or SVG. In the example below, the value in angle brackets stands for the actual lowercase 64-digit SHA-256.

```json
{
  "table": "Drawn from: sha256 <exact-answer-digest>\n\n| Element | Plan section |\n| --- | --- |\n| Folded base | §2 |",
  "no_picture": "The session produced a table only."
}
```

| Identity | Bytes and use |
| --- | --- |
| `answerSha256` | Exact UTF-8 MCP `content` or raw UTF-8 answer file bytes before parsing. Include line endings, final newline and writer trailers. Reject malformed file encoding for a supplied sheet. The table’s first line must match. |
| `draftSha256` | Hash of the actual writer body accepted by the stage after THC’s existing end-marker, trailer and revision processing. Capture it where the stage sets the accepted draft. A stage that produced no accepted draft cannot publish a current sheet. Do not independently guess how to strip a trailer. |
| `currentAtEnd` | Compare the sheet’s `draftSha256` with the last accepted writer-body digest, including dispute. Capture the latter before harness-authored dissent/summary/notice decoration. Same body means current even if wrapper bytes differ. A later change without a sheet makes the latest one stale. |
| Handoff plan hash | Hash the bytes of the actual reviewed `deliverable.md` identified in HANDOFF.md. This is its own identity. Record the sheet’s producing stage and body digest beside it. |

**Storage and publication.**

1. Resolve the saved mode, allowed stage, run root, project root and waiting/duplicate state before touching a supplied path. Validate object shape, hash line, table body, file types from the bytes and bounded sizes. Check that the table is nonempty beyond its digest line. Require the picture extension to agree with the inspected format. An implementation default is the existing `MAX_CLIENT_FILE_BYTES` per table, picture and source file. Read regular files only through contained handles, honor existing path exclusions, bound the actual bytes read, and prevent links or run-folder destinations from redirecting reads/writes. Scan all textual content and user-supplied path/reason strings with existing input rules. Treat drawing code as an opaque attachment. For SVG, store only a static drawing with no active/external content or treat it as unavailable and ask for a PNG/table-only resubmission. Never execute an attachment or inline untrusted markup in the UI.
2. On MCP, integrate at `submitStageAnswer`, before it writes a claim, usage, answer or published sheet. Stage validated bytes under the run privately. Serialize same-stage acceptance or use an exclusive commit with equivalent first-writer semantics. Publish assets and a receipt tied to the answer digest before the canonical answer becomes consumable. The canonical answer is written last. A crash may leave private staging/orphans; replay must ignore or recover them idempotently. Only the winning accepted answer can contribute a report entry. Never erase an earlier valid answer on a retry.
3. On the CLI, the session writes assets and `<stage>.blueprint.json` first when it has a sheet, then publishes the completed `<stage>.md` last. Validate on the path that reads an external answer for replay, *before* it is accepted, cached as complete or used for a subsequent call. A bad sidecar leaves the operator’s input files available for correction and the stage logically waiting. Do not claim the CLI can undo the operator’s writes. A missing sidecar means an intentional answer-only submission. A sidecar arriving after acceptance cannot retroactively attach to it. Document the single-writer convention when using the file route; recheck against the accepted bytes on mixed-route replay so an overwritten file cannot silently rebind a receipt.
4. Keep the existing late-answer behavior. A valid second MCP answer can be retained as `<stage>.late.md` with the existing late usage record. Its sheet is ignored without opening its asset paths. A duplicate cannot unblock another stage, promote a sheet, overwrite a good one or trigger another provider dispatch. Test overlapping submissions, both entry points, interrupted publication, resume twice and a rejected or superseded stage.
5. Write accepted artifacts under `runs/<id>/blueprint/` with harness-generated names for stage/table, image and optional source. Where the same stage may be superseded, use the accepted answer digest to distinguish generations. Report paths are run-relative. Store a digest of each file actually copied. Emit an ordered `blueprint` array (empty when appropriate) with `stage`, `answerSha256`, `draftSha256`, `tableSha256`, `picture` and `code` (each null or `{file, sha256}`), and `currentAtEnd`. The table path is deterministically derivable from stage and answer digest, e.g. `blueprint/<stage>-<answerSha256>.table.md`. Use that convention in the handoff and docs. `blueprintNone` gives the latest accepted sheet’s reason for no picture, or “no sheet handed over” when the array is empty. Omit it after a later valid picture. Preserve stale versus absent as distinct findings in WARNINGS.md and the handoff. Neither condition changes a judge’s vote.

## Handoff contract

Use a dedicated device milestone template assembled by `src/handoff-prompt.js`. Retain the existing Status vocabulary, numbered criteria, milestone headings and machine-readable Entry, Work, Exit and `- check: C1 | <method> => [planned] <observable result>` syntax. Keep the status-insertion anchor “Say which, and why, in the next section.” and a named Verify-first position before parts and materials. Bound each unique insertion to the actual template; exercise both anchors. Apply the existing ending/acceptance clamp to the assembled HANDOFF.md. Preserve the seat’s original status in the report. No hardware-specific acceptance shortcut.

- **Readiness** describes the adequacy of instructions. A later milestone may of course depend on successful work in an earlier one. Routine, specified future checks do not themselves force `partial`. Use `ready_for_build` when every milestone has a credible entry path, named roles, necessary values or an actionable verification with a supported fallback, and checkable exits. Use `partial` when M0 can start but a later milestone has an unresolved blocker; name what can begin. Use `needs_evidence` when M0 requires evidence it lacks and has no supported fallback. Retain existing `needs_decision` behavior for an unresolved decision or an unaccepted ending.
- **Verify first** names each relied-on UNVERIFIED claim, placeholder and part to verify, what would settle it and the plan’s fallback or stop. An unverified claim unused by any step is explicitly marked as such. Copy named components, references, checks and thresholds. Use the request’s exact instrument names. List other required tools by kind under “Instruments to get”. A plan/document inspection can use no instrument.
- **Lint** the raw handoff that the normal run and the standalone command each pass to `lintMilestones`. Check the status clamp separately on the assembled file. Parse leading check tags from `expected`; strip them for the pre-existing nonempty-result check only. A result tag anywhere in the check’s leading tag sequence, including after `[planned]`, yields one `check_reported_done` and takes precedence over `check_untagged`. A missing first `[planned]` yields `check_untagged`. A bare `[planned]` yields `check_without_expected`. Detect a checked Markdown task box on an actual checklist line outside a fence. Ignore tags quoted in prose, examples or source data. Preserve existing findings and criteria-discharge checks. Record warnings in report/WARNINGS.md and “Before you build”. A reviewer checks prose for unjustified claims of success.
- **During building**, the helping session reads HANDOFF.md, the reviewed plan and any BUILD-RESULTS.md and CHANGES.md. At takeover confirm the last actual result or start an empty log. One action at a time, role and hazard note at the relevant step. Record a value with unit and instrument, or a qualitative observation for an inspection, who observed it and when. A hypothetical value never becomes a result. A failed check retains its result. Record a repeat as a separate entry. Ask the person to choose among the plan’s supported routes. A design change affecting a hazard or more than one milestone gets a re-review recommendation. The person controls further debates.
- **After the run**, keep the sealed deliverable and run evidence intact. New checks go into `BUILD-RESULTS.md` as `milestone/check | method and instrument | observation and unit if applicable | passed/failed/not done | date | observer`. Deviations go into `CHANGES.md` as `change ID | plan section | old → new | reason | decision maker | date | plan/sheet identity | re-review status or run`. Mark the reviewed sheet stale for an affected changed design. The helping session maintains these project files. THC gains no physical-build command.
- **Standalone rebuild** resolves kind from `run.json` and uses the original handoff settings/checks from recorded run inputs. Reuse the existing on-build renderer. When a device run's handoff prompt is recorded, prefer its saved context for reconstruction. Preserve applicable endings, objections, file naming, links, thresholds and status clamp in both paths. If evidence required for a faithful device rebuild is missing or inconsistent, identify it, leave existing outputs intact and avoid a paid call. Exercise the standalone external-handoff pause and answer, and its priced dry-run branch, without sending a provider request. Historical software stays on its old route. Do not promise identical model-generated prose on a second call.
