# Unity editor and bridge reference (dated)

*Grades: **D** = read in the primary source (the Unity manual page, or the bridge's source or docs) on the date given; **I** = inference, a secondary report, or something carried from an earlier read and not re-read. "Re-read 2026-10-05" means raw page or file text fetched that day; "carried (2026-10-04)" means taken from an earlier read of the same source dated 2026-10-04. Nothing here was run in a Unity editor by the author of this file except where the measured-run section says so. Every row goes stale: re-verify at each Unity or bridge version change.*

## A. Unity 6000.6 editor facts (manual, re-read 2026-10-05, D)

- **Entering play mode.** The 6000.6 page "Configurable Enter Play mode" says: "By default Unity reloads the scene on entering Play mode" and "By default Unity doesn't reload the scripting domain ... but you can configure it to do so", with "Reload Scene only. This is the default option." The 6000.3 page for the same setting says Unity reloads the scripting domain by default. The 6.6 What's New page says the default **in new projects** is now Reload Scene only; no page read says what an upgraded project gets. So read the project's own Enter Play Mode setting (Project Settings, Editor) before relying on either behaviour; statics, static event handlers and singletons persist between plays when the domain is not reloaded.
- **Resetting statics without a domain reload.** The 6000.6 "Enter Play mode without domain reload" page documents `[OnEnteringPlayMode]` and `[OnExitingPlayMode]` for manual reset (it says resetting on exit is often most efficient, and not reliable for code that also runs in edit mode) and `[AutoStaticsCleanup]` / `[NoAutoStaticsCleanup]` for code-generated automatic reset on entering play mode. The 6.6 What's New page adds that Project Auditor now has a Roslyn analyzer that flags static fields which may need resetting between plays (warnings with the `UAL` prefix, "to support the new default behavior"), and it recommends keeping domain reload off "to prepare for the forthcoming removal of Mono and the domain reload mechanism in future Unity versions" (no version is named).
- **Scripts changing while playing.** Preferences, General, "Script Changes While Playing": *Recompile And Continue Playing* ("This is the default behavior, but you might want to change it if your scripts rely on any non-serializable data"), *Recompile After Finished Playing* (defers recompilation until you stop), *Stop Playing And Recompile*.
- **Play-mode changes.** Game view page: "In Play mode, any changes you make are temporary and are reset when you exit Play mode." That is the scene side. For a ScriptableObject the ScriptableObject page does not say what happens to a scripted play-mode change on stop; it says: "In the Unity Editor, you can save data to ScriptableObjects in Edit mode and Play mode", changes made with the Inspector or editor tools are written to disk, and "Unity doesn't automatically save changes to a ScriptableObject made via script in Edit mode": call `EditorUtility.SetDirty` on it, otherwise the value reverts when the editor is reopened.
- **Safe Mode.** Opening a project with compile errors shows an "Enter Safe Mode?" dialog (a modal prompt). The manual: Safe Mode "never allows managed code to run from your project, or its packages", is "not meant for content production, only for resolving compilation errors", and "Unity automatically exits Safe Mode when it detects there are no more compilation errors". A bridge that is project or package code cannot run in it.
- **Interaction Mode (Preferences, General)** "specifies how long the Editor can idle before it updates", with Default, No Throttling, Monitor Refresh Rate and Custom modes. The same page notes: "In Play mode, Unity ignores any throttling that you apply using this preference." So it can matter for an idle editor in edit mode, and it is **not** an explanation or a fix for a play session that sits at frame 1. What does stall an unfocused play session is not settled by the manual (the bridge's own notes describe a focus nudge for tests; see section B). A frame counter you have watched advance is the check.
- **Editor log.** By default the editor writes "a log file specific to the open project and located in the project folder at ProjectName/Logs/Editor.log"; "Use Global Editor Log" in Preferences or the `-useGlobalLog` argument switches to one global log shared by all projects and editors (on Linux, `~/.config/unity3d/Editor.log`). Know which one you are reading: a global log shared with other editors, or one that stops early, is the wrong evidence. A domain reload leaves a "Domain Reload Profiling" line in the log (seen in one run on 6000.6; the format is not in the manual, I).
- **Object ids** changed in 6.4 and 6.5: see the drift sheet's `EntityId` row.

## B. One bridge at a named tag: CoplayDev `unity-mcp` v10.3.0 (MIT)

*Tag v10.3.0, commit `aa5fc638` (the annotated tag dereferenced through the git refs API) and published 2026-10-04T02:52Z (GitHub releases API); both re-read 2026-10-05. Files marked "re-read" were fetched at that tag on 2026-10-05; the rest are carried from reads of 2026-10-04 (the tag) or of v10.2.0 (marked). Pin a bridge by tag or commit, record the date, and re-read the release notes at each bump. Counts of tools and groups are left out on purpose: they move per release.*

- **Transport and security (re-read 2026-10-05: `SECURITY.md` at the tag; transport details carried from a v10.2.0 read).** HTTP on a loopback address by default (several clients, one pin per client session) or stdio (one client; a new connection replaces the old). The policy says local HTTP binds to loopback only unless a LAN bind is ticked, remote HTTP requires https by default, and remote-hosted mode requires an API key. It also lists as **not** counting as security issues "tool actions that intentionally modify the Unity project (that's the product)" and "issues that require an attacker to already have shell access to the host". So the code-execution, menu-item and build tools are a trust boundary by our reading, not by the policy's own words (an earlier note said the policy names them; the file at this tag does not). That a loopback endpoint carries no authentication, so any local process can drive the editor, is an inference (I).
- **Timeouts and reload (re-read: `plugin_hub.py`).** `COMMAND_TIMEOUT = 30` seconds; `FAST_FAIL_TIMEOUT = 2.0` seconds for state reads while the editor compiles, reloads or is throttled; `retry_on_reload` defaults to true (the server waits for the plugin to reconnect). The editor-side bridge resumes after each domain reload on a schedule of 0, 1, 3, 5, 10 and 30 s (re-read: `HttpBridgeReloadHandler.cs`). Long tools take a longer timeout parameter or run as async jobs.
- **Readiness resource (re-read: `editor_state.py`, `EditorStateCache.cs`).** The server computes "ready for tools" as the absence of blocking reasons: compiling, domain reload pending, tests running, asset refresh in progress, and `stale_status`, which is set when the snapshot's `observed_at` is more than 2000 ms old ("treat >2s as stale"). On the editor side `GetSnapshot` re-stamps `observed_at` only when the application is **not** active; the comment says so ("Re-stamp only in that case so the server-side staleness check still fires for genuinely unresponsive editors when focused"). A focused, idle editor whose state has not changed therefore ages past two seconds and reads as stale. This matches one measured run (section D). Treat the flag as a hint. v10.3.0 also adds a counter of compilations begun in the editor session that survives domain reloads, meant to separate "a compile ran" from "one never started", and a `refresh_unity` compile wait observable across the reload (PR #1347, closed 2026-10-02); whether either changes the readiness behaviour in practice is untested.
- **Replies that succeed without an effect.** Menu items (re-read, `ExecuteMenuItem.cs`): an item that cannot be invoked returns an error, but one that is invoked returns "Attempted to execute menu item ... Check Unity logs for confirmation or errors." whatever the item then does. Assets (re-read: `ManageAsset.cs`): the asset-modify tool returns success ("No applicable or modifiable properties found for asset ... Check component names, property names, and values") when nothing changed, and a reimport that is given importer properties logs only a warning that applying them "is not fully implemented yet". Play (issue #1379, closed 2026-09-04): `play` reported "Entered play mode" when the editor had silently cancelled entry.
- **A timed-out command still runs (re-read: `website/docs/architecture/instance-routing.md`).** "When `asyncio.wait_for` expires ... nothing tells Unity to stop. If the command had already begun executing it runs to completion, and its `command_result` arrives to find no future waiting and is discarded. The caller is told the command failed while its effect landed ... with no idempotency key, a retry cannot be distinguished from a first attempt." The v10.3.0 notes add suppression of broker command resends (PR #1361, closed 2026-09-05); the section above is still in the docs at the tag.
- **Instance pinning (re-read, same doc).** `set_active_instance` stores a pin in session state; with several editors open and no pin the bridge returns the available instance identifiers and asks you to choose; a pin to an editor that has gone costs a 20-second wait and then misreports. Commands that "fail silently" are documented to point at the wrong instance.
- **Code execution (re-read: `execute_code.py`).** "safety_checks blocks known dangerous patterns but is not a full sandbox." Treat it, and the menu-item and build tools, as able to run anything the editor can.
- **Tool groups (re-read: `tool_registry.py` for the default; the HTTP/stdio split carried).** The default enabled set is `{"core"}`; the server enables only that group over HTTP and all groups over stdio; the groups include optional scripting extensions, testing, profiling, animation, UI, VFX, docs and asset generation. Asset-generation tools call remote services with the user's own keys; the v10.3.0 notes add auto-discovery of live fal and OpenRouter asset models (PR #1421, re-read in the release notes). A bridge-vendor skill states that a batch call dispatches by name regardless of group gating (carried, I for how far that reaches). Group gating is therefore not a spending or safety control.
- **Compatibility shims (re-read: `website/docs/architecture/unity-compat.md`, D).** The package ships shims for renamed engine APIs and says of them: "fail-soft: callers should treat a missing API as a no-op, never throw". A fail-soft design can make drift silent; the other face of it is the 6000.6 id stub fixed in this tag (PR #1399, "InstanceIDToObjectCompat NotImplementedException", re-read in the notes).
- **Undo (carried, source grep of v10.2.0; D for the grep, not re-run).** Undo registration was absent from the asset, build, script, shader and texture tools. Whether a later tag changed that was not checked.
- **Telemetry (re-read: `telemetry.py`, `TelemetryHelper.cs`, D).** On by default. Both the Python server and the editor-side helper read the opt-out environment variables (`DISABLE_TELEMETRY`, `UNITY_MCP_DISABLE_TELEMETRY`, `MCP_DISABLE_TELEMETRY`), so set them for both processes (the carried report adds an editor preference).
- **Focus nudge (re-read: troubleshooting guide).** While a test run is silent the server may briefly focus the editor window; `UNITY_MCP_DISABLE_FOCUS_NUDGE=1` in the server's environment turns it off. The nudge uses window-system tooling, so it is platform-specific (carried, I for which one on Linux).
- **Package conflicts (re-read: troubleshooting guide).** With Unity 6.3+ and the vendor's AI Assistant package installed, the bridge's code-analysis dependency can conflict over `System.Collections.Immutable` versions; on Unity 6000.5.x a pre-release AI-assistant-family package can make the editor spin at about 100 percent CPU on startup (documented as Unity bug UUM-132096, not the bridge's). Unity's own page separately says versions 2.13 and later of the AI Assistant package fix a conflict between Unity's CLI and that package.
- **Release-note failure classes (carried from the notes of v10.0.0 to v10.3.0).** A stdio bridge stalling when Unity is backgrounded during a reload; editor state reporting stale while backgrounded; script tools retrying and failing after a reload; compile-flag false positives in play mode; play-mode tests stalling unfocused; screenshots captured before end of frame; the console tool hidden by the console window's own filters (issue #1239, fixed by PR #1342, both closed 2026-09-05); v10.1.2 added a clear-stuck option for the test runner and a deferred-reload fix; v10.2.0 made builds save first and skip never-saved scenes instead of opening a save dialog.
- **Open at the date read (issue states re-read 2026-10-05, D for the state only).** #891 and #1411: an agent is blocked by the "Reload scene" popup (open). #1289: a play-mode screenshot re-enters the player loop (open). #1390: play-mode tests hang the editor on Linux with Vulkan (open). The threads were not read.

## C. Vendor direction and Unity's own agent material

- **Unity's CLI replaces the in-editor AI Assistant MCP server (re-read 2026-10-05, docs.unity.com).** "Unity has deprecated the MCP server included in the in-editor AI assistant package. The Unity CLI replaces this MCP server." The page's table lists "A third-party MCP package installed from GitHub" as not affected, and says `unity command` and `unity eval` "drive the Editor directly, without MCP in between. They're faster and use fewer tokens than MCP." That is about product support; it does not settle any question about terms of use, which the owner or the vendor must answer.
- **Check which bridge the project has installed** and do not install a second one.
- **Unity's first-party plugin for agents (carried, 2026-10-04).** A repository of agent skills with a command-line skill that lists documented failure modes (a bridge that cannot start after a compile error; an unfocused editor that stalls). Its licence is the Unity Companion License for Unity-dependent projects; read for ideas only, none of its wording is reused here.

## D. A first-hand measured run, and what it did not cover

One first-hand trial on a Linux machine, Unity 6000.6.0f1, two bridge versions (a release tag and a later pre-release commit), carried from a report dated 2026-10-02 (I for this file; the rows below are the report's own, not re-run):

- **Measured:** the ready flag read stale while the editor was focused and idle (both versions); an object id failed loudly after every domain reload and a fresh find handed out a working one; `GetInstanceID()` was a compile error in executed code on 6000.6; a menu item's side effect landed; play then stop was confirmed by an executed read; a scene-view screenshot was not black; a domain reload took about 14 s; a console nonce was needed to trust the console tool; the editor and its helper processes together used about 4.8 GiB; the telemetry opt-out was set in both environments.
- **Not measured:** the test runner, undo, a play-mode screenshot, the compile edge through the bridge (compile was proven by a fresh assembly on disk and the reload line in the log instead), the latest tag's server paired with its package, and anything in the open-issue list above.
- **Never run by the author of this file:** Safe Mode behaviour with a bridge, focus throttling, and screenshot staleness on this operating system and Unity version.
