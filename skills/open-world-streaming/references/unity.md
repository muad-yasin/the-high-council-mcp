# Unity: the settings behind the budgets

*Unity 6000.6 manual and scripting API, URP 17.6, HDRP 17.6. Reference dated **2026-10-05**: every page below was read as raw page text against 6000.6 ("Built on 2026-10-03") on 2026-10-04 or 2026-10-05; `sources.md` lists each page with its read date. Documentation-derived, not shipped experience. Unity moves defaults between releases, so check the page for your exact version before relying on a number. Grades: D documented, I inferred; F is a field failure on one project (see SKILL.md).*

## Loading and integration

| Setting | What the docs say | Grade | Use |
|---|---|---|---|
| `Application.backgroundLoadingPriority` | Caps main-thread integration time per frame for all asynchronous operations: Low 2 ms, BelowNormal 4 ms (default), Normal 10 ms, High 50 ms. It governs `Resources.LoadAsync`, `AssetBundle.LoadAssetAsync` / `LoadAllAssetAsync` and `SceneManager.LoadSceneAsync`. **No effect in the Editor; only in a built Player.** UWP defaults to High, consoles to Normal. Profiler marker: `Application.Integrate Assets in Background` | D | Applies only if you stream through those calls. Low or BelowNormal while driving, with lookahead sized from speed; High only behind a loading screen. A streamer that reads its own files is not governed by it |
| Async upload pipeline: time slice and buffer | `QualitySettings.asyncUploadTimeSlice`: 1 to 33 ms, uploads on the **render thread**, unused time is reallocated when nothing is pending. `asyncUploadBufferSize`: 2 to 2047 MB, resized automatically when an asset is larger, at a memory and resource cost | D | Set once from the biggest streamed mesh or texture. Applies to eligible imported assets only (next section) |
| `Object.InstantiateAsync` and `AsyncInstantiateOperation.SetIntegrationTimeMS` | Mainly asynchronous, but the last stage (integration and awake calls) runs on the main thread; the integration time per frame can be capped | D | Prefab-per-cell instantiation with a cap is preferred over additive scenes, or keep cell scenes tiny (I) |
| `Resources.UnloadUnusedAssets` | Walks the whole game object hierarchy including script components, and examines static variables; the script execution stack is not examined, so an asset referenced only from the stack is unloaded; assets other than ScriptableObjects load back on next use. Cost not published | D / I | Never during a drive: a possibly long main-thread pause, plus reloads |
| `AsyncOperation.allowSceneActivation = false` | Progress stops at 0.9, `isDone` stays false, and the whole `AsyncOperation` queue stalls behind it | D | Do not use it to hold a cell while others load |
| AssetBundles | LZMA compresses the content as one stream, and reading an asset means decompressing the entire file into RAM; LZ4 is chunk-based. Per-bundle memory overhead and the claim that LZ4 loads about as fast as uncompressed data were **not re-read** and are I | D / I | Only relevant if you stream through bundles; a project that streams its own tile files does not use this |

## Meshes and collision

- **Async upload eligibility (meshes).** A mesh is eligible only if it is not read/write, not in Resources, has no blend shapes, has no bone weights, its data is not needed by a Particle System, Terrain or Mesh Collider, its topology is not quads, and `meshCompression` is Off; on Android LZ4 must also be enabled in Build Profiles. In all other circumstances Unity loads textures and meshes synchronously (D, 6000.6 make-compatible page). The figure that readable meshes use about twice the memory is I.
- **Meshes built at runtime** through the Mesh API are not covered by that page (I). `Mesh.AllocateWritableMeshData` gives MeshData accessible from any thread, and one call requesting many MeshData is cheaper than many calls; finish with `ApplyAndDisposeWritableMeshData`. `UploadMeshData(true)` frees the CPU copy, but a mesh used for a collider must stay readable in a Player, so free the copy only on render-only meshes (D).
- **`Physics.BakeMesh`** is thread-safe and works from jobs; do not bake the same mesh from several threads at once. In a Player it requires the mesh's Read/Write to be enabled. A MeshCollider reuses the bake only if the cooking options are identical, the transform allows sharing (no skew; negative scale only for non-convex colliders) and the geometry is unchanged. Adding a MeshCollider to an object that already has a MeshFilter sets `sharedMesh` and may trigger a re-bake. The `int` overload is obsolete in 6000.6; use the `EntityId` overload (D). `PlayerSettings.bakeCollisionMeshes` pre-bakes at player build (D).
- **Cooking cost.** Runtime cooking is resource-intensive. `CookForFasterSimulation` toggles between faster simulation and faster cooking; non-default cooking options require a readable mesh. For runtime meshes, mesh cleaning and welding can be disabled to cook faster only if the generator guarantees no degenerate triangles (collinear or near-zero or infinite area) and no co-located vertices (D, prepare-mesh-for-mesh-collider page).
- **Mesh LOD** (manual): LODs are generated at import into the original mesh's index buffer, roughly halving indices per level; the source needs at least 256 triangles; Particle System, Visual Effect Graph and static batching always select LOD0; cross-fade needs GPU Resident Drawer; the manual warns the generator may give poor results on high-curvature meshes or meshes of many disconnected pieces, which describes merged cells (D). `Graphics.RenderMeshInstanced` and `RenderMeshPrimitives` do not select a Mesh LOD automatically and need `forceMeshLod` in `RenderParams` (D). Import-time only; whether runtime-built meshes can use it is I.

## Pipeline states and shaders

- **`ShaderVariantCollection.WarmUp`** is fully supported on DirectX 11 and OpenGL. On DirectX 12, Vulkan and Metal the graphics driver may still do work if the vertex layout or render-target setup differs from what was used to warm up, leaving visible stalls (D).
- **`GraphicsStateCollection`** (namespace `UnityEngine.Rendering`): trace in a development build only (`BeginTrace`, `EndTrace`), one collection per graphics API and platform, then `WarmUp` or `WarmUpProgressively` in the player; `cacheMissCollection` stores the states that were not in the collection during warm-up. Supported on DirectX 12, Vulkan and Metal; DX11, OpenGL, GLES and WebGL fall back to shader warm-up; compute and ray-tracing shaders cannot be traced (D). The 6000.6 manual's page title still says "experimental"; check your version. In a release build `VariantsUploadedToGpuLastFrame` is the available API (D).
- **Mesa and Linux.** Mesa keeps an on-disk shader cache. `MESA_SHADER_CACHE_DIR` sets its parent directory (default `$XDG_CACHE_HOME/mesa_shader_cache`, else `.cache/mesa_shader_cache` under the home directory), `MESA_SHADER_CACHE_DISABLE=true` disables it, `MESA_SHADER_CACHE_MAX_SIZE` defaults to 1 GB, and a separate cache may exist per architecture (D). For a cold run use a fresh empty directory or disable the cache instead of deleting one. Whether a Linux desktop Unity player persists its own pipeline cache is documented for embedded Linux only (D for embedded, not re-opened; unknown for desktop).

## URP feature notes (Unity 6000.6, URP 17.6)

- **Forward** is Unity's recommendation when you do not have many lights or target a low-end platform; Deferred adds G-buffer render passes and a high performance impact. Realtime lights per object: Forward 9, Forward+ unlimited, Deferred unlimited for opaque and 9 for transparent (D, paths comparison).
- **Forward+** removes the per-object light limit by tiled culling, at the price of more shader variants (D).
- **GPU Resident Drawer** works only with: a pipeline asset containing only Renderers using Forward+ or Deferred+; graphics APIs that support compute shaders except OpenGL ES and visionOS; Enlighten realtime GI disabled; GameObjects with a Mesh Renderer that has no MaterialPropertyBlocks, default sorting properties, materials that support BatchRendererGroup, and **no more than 128 materials** (D). Disabling static batching speeds it up. It slightly increases GPU workload, and a GPU-bound application may get slower (D). GPU occlusion culling needs it, tests objects as bounding spheres, and may raise rendering time when little is occluded (D). Whether objects drawn through `Graphics.RenderMeshInstanced` gain from it is I.
- **BatchRendererGroup** requires the SRP Batcher, "Keep All" BRG shader variants and unsafe code, does no frustum or occlusion culling of its instances (you write the culling), and the manual lists **Linux with Vulkan only** (no OpenGL); on a Linux target that may fall back to OpenGL, test the fallback before relying on BRG (D, 6000.6 BRG pages, read 2026-10-05).
- **Upscaling in the URP asset:** render scale with Automatic, Bilinear, Nearest, FSR 1.0 and STP filters. FSR needs shader model 4.5 (otherwise Automatic is used) and stays active at scale 1.0; STP needs compute shaders and shader model 5.0, does not support OpenGL ES, and forces TAA (D).
- **Garbage collection:** incremental collection is on by default; the 3 ms slice is a guideline, not a hard cap, per the manual, and with VSync or a target frame rate Unity uses the idle time at the end of each frame for it regardless of the slice. Too many reference changes make the marking phase fall back to a full non-incremental collection; a full collection also happens under memory pressure; write barriers add overhead on reference changes (D).

## Texture memory

- **Mipmap streaming memory budget:** `Memory Budget` in the Quality settings, default 512 MB. It is shared by mipmap streaming and all mip levels of textures that do not use mipmap streaming (a 100 MB budget with 90 MB of non-streamed textures leaves 10 MB for streaming); estimate it with `Texture.desiredTextureMemory` (D, read 2026-10-05). Mipmap streaming does not support terrain textures, texture arrays, cubemap arrays or 3D textures, and a texture drawn without a Mesh Filter or Skinned Mesh Renderer (for example through `Graphics.DrawMeshNow`) loads the lowest mip the quality settings allow (D, read 2026-10-05).

## Large coordinates

- URP has no camera-relative rendering that we found; the HDRP 17.6 manual describes camera-relative rendering for HDRP only (D for HDRP; for URP, no manual page found on 2026-10-04, so an absence we could not prove). A floating origin you write yourself is the route in URP (I).
