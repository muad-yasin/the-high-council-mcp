# Field lessons - real failure modes, generalized

These are patterns that were actually hit and fixed in a live production, not hypotheticals - kept because the *shape* of the mistake recurs across projects even though the original context doesn't. Read this when a defect "feels familiar" or when reviewing shipped UI/UX work for recurring classes of bug, not just one-off glitches.

## Text/number display

- **A truncation/ellipsis mode can drop content for a reason invisible on screen.** A text element set to "ellipsis" truncation was built with a height budget sized by eyeballing what the font size "looks like it needs." The real measured height at the real column width came out taller than the budget - and the truncation mode's failure axis was *vertical*, not horizontal: it silently dropped the entire line (zero characters rendered, no error, no warning) rather than truncating it with "...". A screenshot of the resulting gap looked like a missing binding, not a sizing bug - the actual cause only showed up by reading the live element's rendered properties, not by looking at the screenshot. **The rule this produced: whenever a text element uses ellipsis/truncation, size its container against the real measured preferred size at the real width - never at what the font size intuitively seems to need.** And a near-identical instance of the exact same class recurred one element away in the same file, on the very next thing built after a comment describing the first instance had already been written and read - a written comment does not reliably stop a repeat; a build-time measurement check does.
- **A displayed rate whose time unit disagrees with the product's own internal clock is a real defect, not a rounding quirk.** Two different screens each converted the same underlying per-second value to a larger unit ("/day", "/hr") using real 24-hour/60-minute arithmetic, while the product's actual internal day was a much shorter interval and the value was only ever earned during a fraction of it. The two displayed numbers disagreed with each other by a large, precise ratio (in one real case, exactly 1.714x, which is 24/14 - the ratio between real hours and the fraction of the day the earning was actually active) - not because the underlying payout logic was wrong (it agreed with itself to the last unit), but because the *display* layer picked a unit basis nobody had checked against the thing it was labeling. **Whenever a display converts a rate into a bigger time unit, verify that unit against the product's actual operating cadence, not just civil-calendar arithmetic** - and if two screens show a "same" number, verify they use the identical basis, because divergence here is invisible until a user notices the numbers don't add up.
- **The same stat, shown on two different screens with two different derivations, is worse than either screen being wrong on its own.** One screen zeroed a value during an "inactive" state; a sibling screen, computing what should have been the same number, read the raw un-zeroed value. Users moving between the two screens saw the underlying reality contradict itself. When this recurred a second time - inside the *same screen*, twelve lines below a comment explaining why the first fix mattered - it confirmed the deeper lesson: **a rule discovered by fixing one specific instance has to be swept from the whole category it belongs to, not just from the examples that happened to prompt it.** A comment that says "fixed here because X" without a mechanical check across every site sharing category X is a promise, not an enforcement.

## Transient feedback and timing

- **A one-shot error/rejection message can be silently overwritten by an unrelated periodic refresh before a user has time to read it.** A "here's why that action failed" message was written into a UI label correctly - and then wiped, about a second later, by an unrelated timer-driven refresh of the same panel that had no idea a message was currently being displayed there. The fix isn't "make the message last longer" (a band-aid); it's recognizing that **any transient, one-shot UI write and any periodic/scheduled refresh that share a render target are in a real race, and the refresh needs to either skip while a message is pending, or the message needs its own dedicated, refresh-immune slot.**
- **A disabled/greyed-out control that correctly prevents an unreachable action can also, as a side effect, prevent a genuinely useful explanation from ever being shown.** If the only path to a specific rejection reason is a tap that a disabled button already blocks, that reason effectively cannot exist for the user - which may be entirely fine (the state was truly unreachable) or may be quietly erasing information a user would have wanted, depending on whether any *other* path can still reach that same rejection. Check this explicitly rather than assuming "the button is disabled, so it's handled."

## Layout, viewport, and lifecycle

- **A cached screen-size measurement taken too early can silently go stale.** Reading a device's viewport/safe-area dimensions at one point in a startup sequence and caching the result, when the OS/runtime settles those dimensions in stages (e.g. an immersive-mode transition finishing after layout already ran), produces a UI built for the wrong size that never gets corrected - because nothing re-measures it once the "real" numbers arrive late. Real-world evidence of the same class of bug: a portrait vs. landscape mismatch that only reproduces on real hardware, never in a windowed desktop preview, because the desktop preview doesn't reproduce the staged-settling timing. **Any cached viewport/geometry read taken at startup needs either a re-check after the platform's own settling signal, or a documented reason it's safe not to.**
- **An app-lifecycle transition (pause/resume, background/foreground) needs an explicit, idempotent reconciliation step - "it'll sort itself out on the next tick" is how state gets duplicated.** A resume handler that recomputed and offered a pending reward, with a guard against overwriting an *already-pending* offer, still had no guard against creating a brand-new one when nothing had been pending - so a normal, repeated background/foreground cycle after the first one in a session could produce more than one reward offer for the same underlying event. The generalizable rule: **treat every lifecycle-transition handler as needing to answer "what happens if this fires twice in a row, or fires when nothing changed" before it ships**, not just "what happens on the one scenario it was written for."
- **A literal, external design mockup should be imported at its own literal values first, and any deviation stated explicitly - not "improved" from memory of what it roughly showed.** A pattern that recurred across several design-import passes: an implementer would recall the *gist* of a provided mockup ("roughly this color", "about this spacing") instead of re-opening the actual file and matching its literal values, and small, cumulative drift from the source accumulated as a result, each individually defensible and collectively a visible mismatch from what was actually signed off. **Treat an approved mockup file as ground truth to re-check at implementation time, the same discipline as re-checking a reference image before a visual decision** - never work from a memory of having looked at it once.

## Contrast and accessibility recurrence

- **A selected/active-state fill color can accidentally equal the text color drawn on top of it, at a 1:1 contrast ratio - and this can ship and go unnoticed for a long time** if the affected row/state is only visited occasionally or the surrounding chrome is loud enough to distract from the specific text being unreadable. This is exactly the kind of defect a real contrast check (computed from a rendered capture, not eyeballed) catches immediately and a visual walkthrough misses for a long time - it's a strong argument for treating the accessibility contrast pass as a mechanical check on every new state-color pairing, not a one-time audit.
