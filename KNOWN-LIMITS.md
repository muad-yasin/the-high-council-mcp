# The High Council: known limits

## Known limits, stated plainly

- **The panel signs one draft; later stages can change what you receive, and nobody re-reads it.** The dispute pass, the post-sign-off challenge and the final edit are model edits made after
  the last review, and the dissent and cold-read blocks are written by the harness. The run labels this and does not repair it: `report.json` has `signed_text` and `delivered_text`
  (hashes, `same_as_signed`, `changed_by`), `BOARD.md` says so when it applies, and `HANDOFF.md` opens with a banner when a model edit changed the text after the panel signed it (a run the panel did not sign keeps its own "not a signed-off plan" banner). A cold-read or dissent block the harness adds is named in `delivered_text.harness_notes` and gets no banner. The panel is not run
  again on the changed text (that would be a further paid pass per run), and `run_status` says so after "every lab signed off" when the delivered text differs (`delivered_text.same_as_signed` in `report.json`).
- **An early finish needs a reviser that is your own session.** On a layered chain the reviser may end its reply with `EARLY-FINISH: <why>`, and the top layer then decides whether the run stops there; that
  works only when the reviser seat is your Claude Code session (`external`). A chain whose reviser is an API seat has no early finish: the line is removed from its text and the log says so. An early finish is not
  agreement: `passed` is false, the run exits 22, and every open objection is a named builder task at the end of `HANDOFF.md`.
- **A run paused before this version can re-run some stages when it resumes (a run paused on 0.8.3 or earlier, resumed on 0.8.4).** From 0.8.4 on, a stage is kept as saved when THC's wording changed between the pause and the resume. A stage saved by an earlier version carries no record of the version that wrote it, so where its saved prompt differs from the one it is asked now it is run again: the run log says `CACHE STALENESS WARNING`, and the new call is paid. To avoid it, finish such a run with the version that paused it. Even from 0.8.4 on, a stage whose prompt differs because a stage before it was asked again, was rewritten in a later sitting or was edited by hand is asked again and paid.
- **A resume after the chain or the task changed asks again every finished step it affects that the run reaches, and a paid chain pays for it again.** A saved stage is kept only when it was made under the chain file and the task the run has now; a stage made under others is asked again when the run reaches it. On a paid chain the limit screen says so before you type a limit: the screen counts the finished steps made under the earlier chain or task, says that each one the run reaches again is asked again, and that the ones that bill are paid again and what they cost before still counts toward the limit (it is a count of what was made earlier, not a promise about the path the run takes). On a chain with no limit screen (free seats or sessions of yours, or a tree member) one line in the run log says how many finished steps the change affects, with the money wording on a paid chain, and each seat that is a session of yours is asked again. A chain file that an update changed is such a change for a run paused before the update. A chain that an update retired is not found by a resume ("No such chain"): copy its file from the repository's chains/outdated/ folder on GitHub (the npm package does not carry that folder) into your project's chains/ folder, and its saved steps are kept when that copy matches the file the run started with. To avoid all of it, finish the run with the version that paused it, or start a new run.
- **A resume after an update keeps saved replies, with two exceptions.** A stage whose reply was repaired after it was saved, and, on a case-insensitive file system (macOS, Windows), the handoff file once it holds its lock block, no longer match their record, so they are asked again after an update and the new call is paid. And a stage is judged by the version and code stamp of the THC that wrote it: two builds that share one version string and carry no code stamp (a packaged binary) are not told apart.
- **A stall below the top layer passes the plan up a layer, and parts of that path have run only with mock seats.** On a layered chain with overseer rounds (your own chain; a ladder chain, which is every shipped planning chain from 0.8.4 on, passes nothing up ahead of its turn) the judges of the next layer up rule on the stuck objections ([AI-README](AI-README.md), "When a layered panel stalls"). These parts of the path have run only with mock seats, so with a real model they are unverified: the ruling, the writer's prompt after a ruling, a sign-off after the plan was passed up, a run that stops after the plan was passed up, and the stop for a stall that cannot be passed up (the top layer holds it; no pass is left; the chain keeps no answer-back list or does not ask its judges to rate; or the next pass is a ladder pass, which does not pass a plan up), which waits for your choice. The plan going up to layer 3 when layer 2 has used its revisions is the same path and has run only with mock seats too. An objection raised again without a quote is known by its judge and criterion alone, so it cannot be told from a new problem under the same criterion and counts as a live objection again; an objection that was passed up once is not passed up again in the same overseer round (a chain without overseer rounds counts the whole run as one round); one raised again with a quote that a ruling closed is recorded and not counted. The ruling prompt does not say who raised an objection, but with `answer_back` the top layer sees every judge's lab in its objection ledger.
- **A persona is a label, not a mask.** All seven shipped planning chains switch `seat_personas` on: `plan-the-high-council` in the form `voice`, the other six in the form `title`. With the chain switch on, each judge or proposer that carries a `persona` has a short block naming it in its own prompts: under the form `title` the block says the name is the title of the seat and changes nothing the seat does; under `voice` (experimental; of the shipped chains only `plan-the-high-council` uses it) every named seat, judge or proposer, speaks in the voice of the name. Nothing stops a judge from writing a persona name in its replies, its own or another seat's, and a voice style can identify a judge across rounds. In the exchange of a layer the other judges read objections with the raiser hidden, and with `answer_back` the top layer sees every judge's lab in its objection ledger. The run counts every persona name found in judge-written text in `report.json` (`seat_personas.names_in_text`) and removes none of them; a name in a proposer's own proposals, posts and replies is not scanned. The same rule holds for every name, alive or not: no setting gives one name less than another.
- **Where the judges rate their objections, a plan can be signed off while objections rated below 4 stay open.** A judge's objection rated below 4 does not hold a sign-off: it is recorded in `report.json` (`severity.swept`; one that was once rated 7 or above and has been re-tagged below 4 is listed in `severity.open_at_end` instead, because it stays open until it is fixed or withdrawn), it still enters the exchange, it does not go to the dispute stage and is not extracted as a claim, and the writer still reads it whenever another objection sends the plan back. The ratings are the judges' own and have not been checked against real model replies, so a judge that rates a real defect low lets it through. The first valid rating a judge gives an objection stands: a later, different rating by the same judge is recorded as an override and does not count. Only the top layer or the person's handler can change the rating in force, and a change across 4 in either direction changes whether the objection holds a sign-off. An objection a judge gives no rating holds a sign-off.
- **The zero-retention setting asks for zero-retention hosts only, and a request cannot rule out one kind of host by itself (0.8.4).** With `--zero-retention on` (or `COUNCIL_ZERO_RETENTION=on`) every call through OpenRouter names only the endpoints that OpenRouter's own list (https://openrouter.ai/api/v1/endpoints/zdr, saved on the date in `src/zdr-hosts.json`) gives for its model as zero-retention hosts, and uses no provider that the list marks anywhere as keeping prompts for abuse monitoring; a seat with no such host is named and the start is refused before anything is sent. OpenRouter's documentation (https://openrouter.ai/docs/guides/features/zdr, read 10 Nov 2026) says a request's `zdr` follows the account's own choice about those endpoints, so a request cannot exclude them on its own: an endpoint of that kind added under a provider name the list allows would match that name until the list is refreshed. The account setting "zero-data-retention only" in OpenRouter's privacy settings rules that out. The setting covers the seats called through OpenRouter only; a seat called straight to its lab is under that lab's own terms. The list is read against its date: more than 45 days after it, a start with the setting on is refused until the list is refreshed with `council refresh-zdr-list`, which fetches OpenRouter's list again (a public request; nothing of your project is sent) and keeps only what this version shipped with, so the refreshed file can narrow the list and never widen it: a host OpenRouter added after this version was released is not used, and a model whose hosts moved is refused, until a newer version ships its own list. The start names the date of the list it used.
- **The start and end lines around the plan are text, and a plan can contain them.** In a chain with `draft_end_marker` on (every shipped chain that reviews a plan has it), and in any chain with prompt caching on, whatever `draft_end_marker` says, a judge's prompt carries a start line before the plan and an end line after it, to mark where the plan is and where the harness's own instructions begin. The plan is shown as written, so a plan that contains the sentence of either line can show a judge a false boundary. The prompt cache takes its breakpoint from the prompt builder, not from the lines.
- **A call that writes a cache entry costs more than the same call without a cache mark, and the entry may never be read (0.8.4).** The marked part of the prompt is billed at the cache-write price, 1.25 times the input price for the 5-minute lifetime and 2 times for the 1-hour lifetime; a later call that reads the entry before it expires is billed less for that part than the plain price. Two of the cases that pay the write and get no read: a pass in which no judge of a layer raises an objection (the exchange does not run, so each judge's verdict call writes the entry and no exchange call reads it), and a later call that starts after the entry's lifetime has passed (it finds no entry and is billed a write again). For Claude called directly, the lifetime is counted from the start of a call, not from the end of its answer, so a slow answer uses up part of it.
- **A cache write can be counted twice in a call's cost (0.8.4).** When a reply says it wrote part of the prompt to a cache and counts those tokens inside the size of the prompt, and THC sent no cache mark with the call, THC prices those tokens at the input price and again at the write price, and a long prompt can be priced at a higher price step. The cost THC counts against your limit is then higher than the bill, never lower. Calls THC marks for caching are counted once. No shipped chain is known to meet this; a seat of your own chain that sets a caching option in its `extra` can.
- **A note after the run is added from a terminal.** The handling session adds a disagreement to the build list after a run has ended with `council note-add`; there is no MCP tool for it, so a handler that has no terminal cannot add one. The note is its own text, up to 600 characters, and it sorts nothing: the objections of the run stay as they were. `BOARD.md` is not re-rendered by a note. On a case-insensitive file system (macOS, Windows) the handoff stage file and HANDOFF.md are one file, so a note adds to the mismatch described above between the handoff file and its record.
- **A summary of the plan is added from a terminal.** The handling session adds a summary and index of the finished plan at the top of deliverable.md with `council summary-add <run folder> --summary-file <file>` (run it without the file to see what to write); there is no MCP tool for it, so a handler that has no terminal cannot add one. It needs a handling session, it can be added once, and the run's closing summary names it. The block says how the run ended in the words THC uses elsewhere; the rest of the file is as the run wrote it.
- **A ruling is given from a terminal (0.8.4).** `council ruling-add <run folder> --ruling "<text>"` asks for a ruling that the judges and the reviser read from the next pass on, and `council ruling-withdraw <run folder> <gate>` takes an approved one out of force from the next pass; there is no MCP tool for either, so a handler session without a terminal cannot give or withdraw one. Each waits at an approval for a day, and the run does not go on until it is answered or has expired: the person answers with `council gate answer`, or, for a request the handler session made itself (`--relayed`), the handler session relays the answer with `council relay-answer` and the person's own words, which are accepted for a ruling only if its text is in them. `AI-README.md` has the details.
- **A plan the panel did not agree on is accepted, or not, by a person or the handling session (0.8.4).** After a run that ended without agreement, `council accept <run folder> --reason "<why>"` (a person at a terminal) or step `accept` of the `stop_decide` tool (the handling session) records that the plan is accepted as it stands: who, when, why and which open objections stand. It agrees with no judge and changes no objection; the handoff keeps its banner and gets one line under it and its Status back. The session may accept on its own authority only when no stop of the run was the person's and the text is the text the panel last reviewed; otherwise the person accepts, at a terminal or by telling the handling session, which relays the person's own words (`person_words`) and is recorded as the person's, relayed. `AI-README.md` has the details.
- The spend cap is checked against an **expected cost**, not a worst case. Before each call THC prices the whole prompt as
  input plus the output that kind of call usually writes (the sizes the dry run uses, never above the seat's `maxTokens`), adds
  what it has counted and the expected cost of the calls in flight, and refuses the call if the total passes your limit. A re-ask,
  a retry of a cut-off reply and an Anthropic seat's retry after thinking used its whole budget are checked at the expected cost of
  the call they repeat. A call with no expected size (a merge, a full revise, the conflict decider, the allocator) and an answer-back call
  (`-answered`, `-question`, which is not a re-ask) are checked at their worst case: the whole prompt as input plus the seat's entire
  `maxTokens` as output. **A run can therefore end above your limit when its last calls write more than expected.** A
  call checked at an expected size can write more than that, up to its whole `maxTokens`. A re-ask or a retry that costs
  more than its expected cost is one case of this. A long call that passes a price step its estimate did not reach is
  another: the check counts a call at the price step its estimated size reaches (the price-step limit below says what is
  not verified). A call of a layer's exchange (a post or an answer, in a pass or in the exchange that closes a run that
  ended without the top layer's sign-off) is a third: it is checked at the size the dry run prices it at (a seat's review
  size: 5,000 output tokens on the shipped planning chains for most seats) and not at the seat's whole `maxTokens`. In the
  author's bench runs the median post of several cheaper models was larger than that size; no call of the exchange that
  closes a run has been measured. What a call reserves on disk before it is sent is still its worst case. A run that stops at its limit keeps
  what it paid for: resume it, and a paid run asks for a new, higher total on the limit screen (a chain with no paid seat takes `--max-usd`).
- **A resumed run can count a paid call against your limit differently from the report (0.8.4).** A paid stage file that the resumed run never asks for again (an earlier sitting wrote it, and the new path no longer reaches its stage) is counted in the report and in `council --spend`, not against your limit, so the resumed run can spend that file's cost on top of the limit you typed. A reservation THC wrote before a call and never closed, beside a usage or charge file of the same call, counts against your limit at its worst case plus the file, while the report counts the call once, at the larger of the two: the limit has less room than the report suggests.
- The dry run (`--dry-run`, MCP `dry_run`) prices the task alone and does not read `--context`
  documents, so for a run with context its estimate is too low. The spend cap is not affected: it
  checks every real prompt, context included, before each call.
- A seat whose model has no price, neither in `src/pricing.json` nor in your project's `pricing.user.json`, cannot be held by a spend cap, because the cap would count every call to it as $0. Since 0.8.2 a run **refuses** such a
  seat before it sends anything (exit 5; the message names the seat and, since 0.8.3, the way out: add a row for it to `pricing.user.json` in your project folder, for example `{ "openrouter/vendor/model": { "in": 1.0, "out": 4.0 } }`, in US dollars per million tokens; your row can add a missing price or raise a shipped one and can never lower a shipped one, and a file that cannot be read in full is refused as a whole), and
  `--dry-run` shows the same refusal at $0. `mock`, `external` and `ollama` seats are exempt: `ollama` prices at an explicit $0 for any model name, because it is genuinely free to run.
  What remains: the cap is only as good as the price table (it is dated, and the dry run says when it is old), and a model that answers in place of a priced one (an OpenRouter fallback in
  `extra.models`) is charged at the priced seat's price, which can differ from its own.
- A call that fails **after** it reached the provider - the connection drops while a 200 reply is
  being read, a 200 carries a body that is not JSON, or the request times out waiting for headers -
  was probably already billed, and its real usage cannot be read. A body that is not JSON and a
  request that timed out are not sent again: each is counted toward the per-run cap at its
  worst-case projection, and recorded as `superseded/<label>.charge-<n>.usage.json`, which
  `council --spend` and a resume count. A connection that dropped is sent again, at most three times:
  for a seat that bills, three in a run (every stage and every re-ask of the run share them, and
  they are kept in the run folder, so a resume you start does not give them back); for a seat that
  does not bill (`mock`, `ollama`), which leaves no charge to count, three in a sitting (a resume
  you start has three of its own). Every resume is a line in `run.log`, and a seat that does not
  bill also gets a line in `network-resumes.jsonl`. The failure after the third stops the run
  (exit 16, `STOPPED-error.json` with `causeClass` `transport`), and you can resume it. A stage that
  two earlier attempts were already counted as possibly billed for is not sent again. Each attempt
  of a seat that bills is gated by the cap, reserved before it is sent and counted on its own: at a
  typical cost for the call (its expected cost when the dry run plans it, else a typical size for
  what it writes, never more than one attempt's worst case), so the counted total can be
  lower than the bill. The deep dive and the side commands that make one call
  (`digest`, `handoff --from-run`, contract drafts) do not send a dropped connection again.
  A 5xx answer means the request reached the provider; it is sent again, at most twice for each ask
  (a 5xx on the second ask of a call that retries a cut-off reply starts the call again, so its first
  ask is sent and paid again). The deep dive and the side commands that make one call (`digest`,
  `handoff --from-run`, contract drafts) are not sent again after a 5xx. For a
  seat that bills, every re-send is gated by the cap, reserved before it is sent and recorded in
  `spend-reservations.jsonl`; a seat that does not bill leaves only a line in `run.log`. Such an
  answer carries no usage figure, so for a seat that bills THC counts each 5xx attempt at a typical
  cost for the call (its expected cost when the dry run plans it, else a typical size for what it
  writes, never more than one attempt's worst case), records it as
  `superseded/<label>.charge-<n>.usage.json` and marks it `reachedProvider`. A provider may not bill
  a 5xx at all, so the counted total can be higher or lower than the bill. The dry run's upper
  estimate leaves out these repeated attempts after a provider error, while the counted total
  includes them. Those 5xx attempts
  count for the rule above: when a stage is run again, for example by a resume, one with two of
  them behind it is not sent again after a dropped connection. A 429 and a failure before anything
  was sent are sent again free and unrecorded.
  A 200 whose body is an error and carries no reply is the provider saying what happened, so THC
  counts it toward the cap at the usage figure the body reports, else at a typical cost for that
  call (the expected cost of the call, or of the call it repeats, and for a call the dry run does
  not plan a typical size for what it writes; never more than one attempt's worst case), and
  records it the same way.
- Some hosted reasoning models stop at a provider-side reasoning ceiling well below the seat's own
  cap, before writing any answer (seen 2026-09-23: `deepseek/deepseek-v4.1-flash` via OpenRouter, 6 of
  28 calls stopped at ~4.2k tokens, all reasoning, under a 36k cap). A bigger cap cannot fix that, so
  such a reply is recorded as `REASONING_EXHAUSTED` and is not retried: the seat abstains, which
  blocks unanimity and never counts as consent. Whether to change a chain's reasoning settings for it
  is a roster decision, not something the harness does for you.
- **The Claude Code plugin installs from the repository root.** `claude plugin validate .` passes with one warning, and
  `claude plugin validate --strict .` fails on it: "CLAUDE.md at the plugin root is not loaded as project context" (the
  file is this project's own instructions and is not part of the plugin). A separate `plugin/` directory would not have it;
  that layout was declined for 0.8.1 and comes back with the plugin directory listing. What Claude Code passes for an
  unset optional dialog field was seen once, in a scratch plugin on Claude Code 2.1.289 (an empty string), not across
  versions or on Claude Desktop's own client.
- **The reasoning fields were set from the providers' documents and OpenRouter's public model list,
  not exercised in a live call** (src/reasoning-table.json; its `asOf` field is the date they were read). A provider that rejects a
  field fails that seat's call with the provider's own error; the first real run of a changed chain is
  the live test. The table turns stale after 60 days and a release test fails then. Seats that now
  reason at high use their output cap faster, and a cap sized for a short answer (a questions or criteria
  stage) can be spent on thinking: such a seat is retried once at a bigger cap and, past the limit, is
  recorded with no answer. A direct Anthropic call is streamed (0.8.4), meant to get past Node's 300 s wait for response
  headers. One real call has run on that path (Sonnet 5.5, Node 22.23.4, 24,408 output tokens in 168 s): its
  headers came back within a second, and it ended before 300 s, so no real streamed call has yet been seen to
  run past 300 s. Its retry stays bounded at 64,000 tokens. A silence inside the stream (Claude 5 does not
  stream its thinking unless asked, and Anthropic documents no longest gap between events) is ended by Node's
  own 300 s limit between pieces of data: the longest silence in that one call was 15 s, and nothing longer
  has been measured.
- Prices in `src/pricing.json` are hand-maintained list prices. Its `asOf` date (2026-10-23: the
  oldest date every entry was last checked) is printed by `council doctor` and `--dry-run`, with a
  warning once it is more than 60 days old. A model whose provider has retired it or no longer
  lists a price keeps the figure the table already had for it, and its row's `_source` says so:
  the date records the read, not that figure. The spend cap and every estimate use these static
  prices. They are estimates, not invoices. Your provider's bill is the real number. A row whose
  price is known to change carries an `expires` date (Gemini 4 Argon, whose price doubles on
  2026-12-01; Gemini 3.8 Flash and Gemini 3.6 Flash, whose prices double on 2027-01-01). Once a row's date has passed, `council doctor` and
  `--dry-run` warn, but until the table is updated the projection and the cap keep the old price:
  a call straight to the lab can then cost more than they project, while a call through
  OpenRouter stops the run instead of overpaying.
- The retired `plan-highest-7` (in `chains/outdated/`) was never run with real models, and `plan-daily-7` ran once (2026-09-28) with the roster it had before the 7 Oct 2026 redesign. None of the tiered councils' mechanisms (tiers, the deep-dive seat, the majority
  guard) has been measured. Their dry-run prices are projections.
- **`run_tests` runs a repository's own test files as trusted code, with no sandbox.** It belongs to the opt-in seat tools (`verify.tools` naming `run_tests`; no shipped chain does; a seat
  may request it mid-stage only when the chain also sets `tools.seat_requests`). Since 0.8.2 the test process gets an allowlisted environment: `PATH`, `HOME` (`USERPROFILE`), the temporary-folder
  variables, `LANG`, `LANGUAGE`, `LC_*`, `TERM`, `CI` and the Windows system variables (`SystemRoot`, `ComSpec`, `PATHEXT`, `WINDIR`). No provider key is in its environment, but a test is code you trust: it can still read the parent process's environment and files on disk (for example `/proc/<pid>/environ`). A project's tests that need another
  variable (a database URL, say) will not see it. It can still read every file you can read, write files and use the network, so use it only on a repository you trust.
- **The symbolic-link containment of the MCP tools is untested on Windows.** Since 0.8.2 the tools refuse a run folder that holds a symbolic link and open run-folder files with `O_NOFOLLOW`. That flag does not exist on Windows, so there the
  protection rests on the `lstat` checks alone, and it has been tested on Linux only: not on a real Windows machine, and the packaged `.exe`'s smoke test under Wine does not exercise it.
- Seats marked `external` (the decider and the writer seats of every planning chain, and the seats answered through your Claude subscription) pause the run until someone answers them, and are $0 only because a Claude Code
  session on a subscription, or you on your own plan, writes them. Nothing checks who wrote the answer.
- Chains with many labs and high round caps get expensive quickly: every round asks every critic seat. Price
  before you run.
- A panel that signs off is not a guarantee the output is correct. It means every critic seat
  checked it against the stated acceptance criteria and found nothing. Criteria that are vague
  produce sign-offs that mean nothing - the quality of the run depends heavily on the quality of
  the criteria stage.
- Some chains pause for human input by design. They are not stuck.
- The audit log (`audit.jsonl`) detects an edited line or a cut-off end, but **with no HMAC key,
  which is the default, it does not detect a full rewrite**: anyone who can edit the file can
  recompute every hash. Set `AUDIT_HMAC_KEY_FILE` to a key kept outside the run folder if the log
  has to stand up to that.
- The run folder of any run holds the absolute path of your working folder (`run.json`, `run.log`, `RESUME.md`): committing a run folder publishes it. `write_task` and `start_run` send text to the labs with no preview, only the key scan, the personal-data check (it stops the run at a finding unless you set `COUNCIL_PII_GATE` to `warn`) and the spend cap.
- The outbound key scan matches **key shapes only**, the formats in `src/secret-patterns.js`; a
  password written in prose is not detectable. Generic shapes (a password inside a URL or an
  assignment) are checked in your inputs before the run; text the models write is checked only for
  distinctive key formats.
- **The contract record (`council contract`, `contract_read`, `contract_amend`) was checked only against mock providers and a pretend terminal.** Its drafting call was never made with a real model
  (its wording, recorded in 0.8.2, has only been read by a mock seat). The person's answer is friction, not enforcement: a shell-capable agent can open a pseudo-terminal, as
  with `council gate answer`. A contract is an agreement between a person and a build session's instructions; it does not make a build session follow it, and nothing here measures whether it helps.
- **The approval gate is friction, not enforcement.** A contract is approved at a terminal, a typed spending limit at a terminal or in the client's dialog, and the terminal answer can be typed by anything that runs as you. The gate's ledger is
  tamper-evident, not tamper-proof: an edit before its last line is detected; the last line, the tail and a rewrite of both the ledger and its view are not.
- **A planning run can be asked to pause from outside, but only at the next pass boundary.** `council pause <run folder>` asks a running run to pause after the pass it is in; the run stops before the next pass is started, written or paid for. It refuses a run nobody is running and a tree member.
- GPT-6 Astra is reachable only through OpenRouter: there
  is no subscription route.
- **A review cut-off in the security-review seat:** `src/security-review.js` cuts reviewer fields at 2,000 characters with a visible marker and no record.
- **Untested on case-insensitive file systems (macOS, Windows).** The fix for `handoff.md` and `HANDOFF.md` being one file (FX-9: `handoff --from-run` now also writes with an exclusive create, so it cannot replace an existing file whatever the disk's case rules) and the working-folder path checks were tested on Linux only. No pass on a Mac or a Windows machine was run for 0.8.1 or 0.8.2.
- **The dry run's expected figure does not price every cap.** A planning chain's expected figure prices a critic at the chain's own estimate, not at its output cap, so the larger caps of
  0.8.1 and 0.8.3 (now 393,216 tokens for DeepSeek V4.1 Flash) appear in the dry run's upper estimate, not in the expected figure; the spend check prices a call at its expected size, so only a call with no expected size (a merge, a full revise, the conflict decider, the allocator)
  is checked at its worst case with those larger caps, and such a call can stop a run before the expected total. - **A host preference rests on documented ordering and one undocumented interaction (0.8.4).** `provider-preference.json` in your project folder asks OpenRouter to try the hosts you name first for a model (`provider.order`, full endpoint tags such as `azure/us` or `wafer/mxfp4`) and leaves `allow_fallbacks` on, so any other host can still serve a call that none of yours can. OpenRouter's routing page (read 2026-11-01) says the router "will prioritize providers in this list, and in this order" and "will try them one at a time and proceed to other providers if none are operational"; it does not say how `order` combines with `provider.max_price`, the price filter every call carries. THC assumes the filter applies first and your order among the hosts that pass it; that has not been probed. - **A relayed choice at a stop, or a relayed acceptance of a plan, is the handling session carrying the person's own words (0.8.4).** `stop_decide` over MCP with the choice `continue`, `finish` or `finish_now` and `person_words` answers a stopped run at any stop on the person's behalf, and step `accept` with `person_words` accepts a plan the panel did not agree on. `finish_now` ends the run at once, with no judge asked again (a final read already on disk for this text is kept and counts as read): inside the review rounds the run ends not agreed, and at a spending stop or a credential-shaped pause after them it keeps the verdict the rounds reached, and so does a panel that had signed off at the stop where no seat of the top layer could read the final plan; a relayed `continue` may carry `rounds`, which does what `--rounds N` does at the terminal (on a ladder run, the new total of top-layer reads). The tool cannot verify that the person gave those words: the gate ledger writes the answer as the session's (actor `main-session`, channel `session`, the words beside it), the run's record of the choice carries the actor `person`, marked `relayed`, with the same words, and every line that names who ended the run says the handling session relayed it, where a choice typed at a terminal shows the channel `cli` and the actor `unknown`.
