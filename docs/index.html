A planning harness that runs one idea past several AI models from different labs, makes them argue about it on the record - proposals objected to, withdrawn, revised, held - and stops at a checkable result.

Nothing is resold, nothing is hosted for you, and no key ever leaves your machine.

On what this does and doesn't claim

This repo publishes the mechanism: the chains, the seat rosters, the stage order. It does not claim to produce better plans than a single good model would. That is an open question and we have not measured it. What it does, concretely, is make disagreement between models visible and recorded instead of averaged away - you can read who objected to what, who withdrew a proposal under argument, and who held their position.

How it works

A run moves through fixed stages. Which stages fire depends on the chain you pick.

Questions → Criteria → Skeleton → Proposals → Debate → Build → Panel review → Handoff
01Questions

A seat reads the request and asks only the questions whose answers would change the output. You answer them, or take its stated defaults.

02Criteria

The request becomes a short list of acceptance criteria, each one a yes/no check rather than a matter of taste.

03Skeleton

An outline the other models will propose against. Names the parts, decides nothing.

04Proposals

Every lab proposes buildable parts, blind to each other.

05Debate

The labs read each other's proposals, anonymised, and post support / object / merge. Then each author replies: keep, amend, or withdraw.

06Build

One seat integrates the surviving proposals into a single document.

07Panel review

Every critic independently grades the draft against the acceptance criteria, blind. Not unanimous? It revises against the union of every objection and the panel reviews again, up to the chain's round cap.

08Handoff

A HANDOFF.md written for whoever executes the result.

Every run writes a folder: the deliverable, BOARD.md (the full debate - every post, every withdrawal), HANDOFF.md, a per-lab scoreboard, and the real token/cost accounting.

Setup

Node 20+, plus API keys for whichever labs your chain uses.

git clone https://github.com/muad-yasin/the-high-council-mcp.git
cd the-high-council-mcp
npm install
cp .env.example .env

Fill in .env with only the keys your chain needs:

ANTHROPIC_API_KEY OPENAI_API_KEY GOOGLE_API_KEY MISTRAL_API_KEY DEEPSEEK_API_KEY GROQ_API_KEY TOGETHER_API_KEY COHERE_API_KEY OPENROUTER_API_KEY ZAI_API_KEY XAI_API_KEY

The CLI refuses to start if any seat in the chosen chain is missing its key, rather than failing halfway through a paid run.

Quick start

Write what you want into a task file, then run a chain against it.

mkdir -p tasks
echo "What I want planned, in plain words." > tasks/your-idea.md

# see what's available and what it would cost
node src/cli.js --help
npm run dry -- --task tasks/your-idea.md --chain verify

# a real run
node src/cli.js --task tasks/your-idea.md --chain verify

verify is the cheap default: two labs, a hard two-round cap. Start there.

Or run it as an MCP server and let your client drive it:

npm run mcp

The spend cap

$5
per-run ceiling by default, checked before each paid stage

A stage that could take the run past the ceiling is never called, so the cap holds rather than reporting the overspend afterwards. A run that hits it stops cleanly and writes STOPPED-budget.md. Nothing is half-written - continue it with a higher ceiling and completed stages replay from disk for free.

node src/cli.js --task tasks/x.md --max-usd 2      # this run stops at $2
node src/cli.js --task tasks/x.md --max-usd none   # no ceiling
node src/cli.js --resume runs/<id> --max-usd 10    # continue with headroom

Chains

44 chain configs live in chains/. Each one is plain JSON - the seat roster, which models fill which seat, the round cap, and whether proposals/debate/handoff stages run. They are meant to be copied and edited.

verify
Two labs, two rounds. The recommended starting point.
cheap
Small models throughout. For testing the harness itself, not for real work.
plan-debate
Five labs propose blind, debate each other's proposals anonymised, then a blind panel grades the integrated draft.
plan-auto
The full open-scope chain, every seat on a real API, runs unattended end to end.
plan-unanimous
Every critic must independently sign off on the same draft. Three rounds here means up to fifteen critic calls, not five.
mock-budget
Calls no API but carries fixture prices - watch the cap work without spending anything.

Read a chain's description field before running it; they say what they cost you in calls.

New in v5

Ten additions, mostly opt-in and read-only - a chain you already have keeps behaving exactly as it always has unless you deliberately use one of these.

council init
Writes a starter chain and task file into your own directory, prices it with no network call, then runs a real all-mock $0 run end to end - the first artifact a fresh clone produces is a real run folder, not just terminal output.
council doctor --chain <file>
Fail-loud lint of one chain config - missing stage contracts, unreachable stages, unrecognized providers - before anything metered ever runs against it.
council doctor --scan-artifacts
Scans your own task files and chain configs for key-shaped strings before you commit or share them. Reports the file and line only - the matched text itself is never printed.
--forecast-cost --chain <name>
A realistic USD range from that chain's own run history on this machine, repriced at today's rates - distinct from --dry-run's worst-case estimate from the chain's declared token assumptions.
export-board --run <folder> --out <file>
A run's proposals, debate and verdict rendered into one self-contained HTML file - no external assets, no server, nothing to install to read it.
replay --run <folder> [--json]
A numbered, step-by-step transcript of a run's reasoning, for reading a run without opening its raw files - --json for a machine-readable form.
schemaVersion
An optional field on a chain config. council doctor warns, never fails, when it's missing or older than current - a chain file that predates this is read exactly as it always was.
max_proposals_per_seat
Opt-in only - there is no default. A chain may declare how many proposals one seat's own list may carry to the debate board; a seat that returns more gets one prompt to fold its own proposals down first. A chain that never sets this field behaves exactly as it always has - debate size stays unlimited unless you deliberately choose otherwise.
stage-log.jsonl
One JSONL line per stage, written into every run folder alongside the existing markdown and report.json artifacts - seat, lab, token counts, cost and timing only, never prompt content.
CONTRIBUTING.md
Names the three smallest contribution shapes this one-maintainer repo can review quickly: a new provider adapter, a new chain config, a new mock fixture.

Inside a debate round

Seven mechanisms that shape what a debate round actually does, each opt-in and gated behind its own config key - a chain that sets none of them behaves exactly as it always has. Described mechanically, what each one does, not what it's for.

1
verify.enabled
A seat's own reply can invoke a fixed, sandboxed allowlist of four offline tools - run_tests, check_versions, grep_repo, read_file, no generic shell, no network. Every result is appended verbatim to the run's ground_truth array and re-presented unedited to every later seat - a claim gets checked against real output mid-debate, not just argued back and forth.
2
allocator.enabled
After a normal panel round, one extra round runs targeted at whichever single criterion the critics actually split on - the one with the most FAILED votes - instead of re-reviewing the whole draft uniformly. Scrutiny goes where the panel actually disagreed, not everywhere at the same depth.
3
descending: true
Each round debates a new, frozen object in sequence - plan, then architecture, then edge cases, then code by default - rather than re-litigating the same draft. An amendment that targets an already-frozen stage is rejected before it can apply, enforced at the executor level, not left to a critic's own system prompt to self-police.
4
freedoms.blocking_questions / .pass
A critic seat may ask one blocking question that pauses its own round until the proposer answers, or pass with a stated reason - instead of being forced to render a meets/fails verdict on something it has no real basis to judge.
5
challenge.enabled
After signoff, exactly one seat may raise exactly one challenge against exactly one decision, for exactly one extra round - the bound is hard-coded in the executor, not a configurable limit, so the narrowness of the re-open can't be loosened by a chain file.
6
canary.enabled + sampleRate
In a sampled fraction of runs, one deliberately wrong, evidence-free objection is injected against a real surviving proposal after the real debate round already finished, and the author answers it exactly like a real post. Whether it capitulates or holds is recorded, never applied to the plan itself - and structurally excluded from every real metric this project reports, so a canary can never inflate a number about the debate mechanism's own engagement.
7
claims.enabled
An objection gets restated as a typed {claim, evidence} pair rather than staying free text. The evidence is checked offline, no second model call: a quote must appear verbatim in the actual draft, or a tool reference must name a real entry this run's own tool-grounded verification produced - not prose asserting something happened.

Known limits, stated plainly

The spend cap is enforced against a worst case, not a prediction: the whole prompt billed as input plus the seat's entire maxTokens budget billed as output (doubled for Anthropic seats, which may retry once). Real stages almost never cost that much, so a run can stop with headroom left. That is the intended trade - resume it with a higher ceiling.

A seat whose model has no entry in src/pricing.json is unpriced, and therefore uncapped. It contributes $0 to the running total no matter what it really costs. Check dry_run output for unpriced before trusting a ceiling.

Prices in src/pricing.json are hand-maintained list prices, last verified 2026-09-06. They are estimates, not invoices. Your provider's bill is the real number.

Chains with many labs and high round caps get expensive quickly. plan-unanimous at three rounds is fifteen critic calls; plan-auto runs several frontier models over multiple rounds. Price before you run.

A panel that signs off is not a guarantee the output is correct. It means every critic seat checked it against the stated acceptance criteria and found nothing. Criteria that are vague produce sign-offs that mean nothing - the quality of the run depends heavily on the quality of the criteria stage.

Some chains pause for human input by design. They are not stuck.
