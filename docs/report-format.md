# The run format (`report.json`)

Every finished run writes `runs/<id>/report.json`: the whole run as data. It holds the acceptance
criteria, every proposal, every debate post and reply, each reviewer's sign-off or objections, what
the plan did with each proposal, and what every model call cost. `BOARD.md` is the same record for
people. If you build something on top of a run, read the JSON. Do not parse the markdown.

The format is published as a JSON Schema (draft 2020-12): [`schemas/report-v1.json`](../schemas/report-v1.json),
shipped in the npm package too. Every top-level field in it has a description; a nested field has one where its meaning is not clear from its name.

## Versioning

- `schemaVersion` (an integer, first key in the file) names the format version. It is `1`.
- It changes only on a **breaking** change: a field renamed or removed, or its type or meaning
  changed. A breaking change gets a new schema file (`report-v2.json`) and a changelog entry.
- **Adding a field is not breaking** and does not change `schemaVersion`. Ignore fields you do not
  know. The schema leaves `additionalProperties` open so an older reader still accepts a newer report.
- A `report.json` with no `schemaVersion` was written before 0.7.7. Read it as version 1.
- This is separate from the `schemaVersion` a chain file may declare. That one versions
  `chains/*.json`; this one versions `report.json`.

## Stable and experimental fields

Each top-level property in the schema carries `"x-stability": "stable"` or `"experimental"`.

- **Stable** fields keep their name, type and meaning for all of version 1: `schemaVersion`, `runId`,
  `chain`, `task`, `fromRun`, `criteria`, `questions`, `passed`, `outcome`, `lastCritique`,
  `signoff`, `proposals`, `dropouts`, `debate` (`posts`, `replies`), `scoreboard`, `totals`, `maxUsd`,
  `stages`, `alternatives`.
- **Experimental** fields belong to newer or opt-in stages. They may change shape in a minor
  release, and the changelog says so when one does. Examples: `panelVerdicts`, `dispute`,
  `disputes`, `security_review`, `claims`, `lints`, `argued`, `debate.diagnostics`,
  `debate.dropped` (since 0.7.8: the debate posts and author replies the harness rejected, per lab
  and reason; `[]` when none were), `notQuorate` (since 0.7.8: only on a chain that sets
  `quorum.minHeard`, when a round's sign-off had too few verdicts to count), `deep_dive` (since
  0.7.8: only on a chain with a deep-dive seat, what it checked and found, and what it cost).
  Also since 0.7.8, with the majority guard on, a `debate.replies[]` withdrawal that does not quote
  the argument it concedes to carries `unargued: true`, and its proposal stays for the builder.

Since 0.8.0 (all experimental, all additive, none read by any verdict, prompt or stop):
`criteria_lints[]` ($0 word-level findings over the criteria list, run before any paid round: no
criterion asks the plan to be consistent with itself, most criteria only ask that something be named,
a vague word with no number or check; `[]` when clean, never a stop), `criteria_sha256` (a fingerprint of the criteria list, the same one the lock block at the end of
`HANDOFF.md` carries; `council check-lock HANDOFF.md --run runs/<id>` compares them), `checks_sha256` (since 0.8.1: a
fingerprint of how each criterion is checked, its `check` and `on` from `criteria_kinds`, null for the others; the lock block
lists each check under its criterion and carries this hash in a second marker, which `check-lock` verifies too), `thin_contract` (0.8.2, experimental: one record of the task, criteria, checks, evidence and signed text hashes, all 64-hex, plus `sha256` over the record without that field: canonical JSON, keys sorted at every depth, no whitespace, UTF-8, an unknown component the literal null; `evidence.ground_truth_sha256` is over each shown `{ tool, args, result }` without `result_ref`; `council contract check runs/<id>` recomputes it, and it is tamper-evident, not tamper-proof; absent for an advice run), `handoff_milestones` (0.8.2, experimental, only when the chain sets `handoff_contract.milestones`: `{ status, milestones, findings[] }`, what a $0 lint found in the milestones the handoff seat wrote; never changes `passed`), `criteria_ids` (positional, index-aligned with `criteria`: `C1`, `C2`, ...) and `missing_criteria[]`
(sign-offs whose criteria table left criteria out, by round and lab; `[]` when none did, and a reply
with no table at all is not listed); `cut_despite_support[]` (proposals the plan cut although another
lab supported them in the debate, with supporters and objectors; only when the run had proposals and a
debate); `disagreement_map[]` (one row per review round: each lab's verdict, `(carried)` when it was
reused on an unchanged draft).

Since 0.8.4 (a stall passed up a layer, or layer 2's revision limit sending the plan up to layer 3; AI-README, "When a layered panel stalls"): `escalations[]` (with `stalled`: the objections that reached the stall window and the passes they stood in) and `escalated_signoff`, `panelVerdicts[].sustained` and `dispute.open_objections[].escalated_standing`, and new values in closed lists: `escalated` in `layers[].state` and `decisions[].why`, `layer2_bound` in `escalations[].trigger` and `layers[].escalated_by`, `escalated_signoff` in `dispute.reason`, `escalated_signoff_block` in `delivered_text.harness_notes`. `dispute.reason: "stalled"` now means a stall that ended the review of a chain without layers; on a layered chain a stall that cannot be passed up is a stop (see the stop block below). Since 0.8.2, `panelVerdicts[].lane` (additive, only for a seat with a review lane, the optional `plan-lanes-4` chain, since 0.8.3 in `chains/outdated/`). Since 0.8.1 (optional and additive, none read by any verdict, prompt or stop): `field_cuts[]` (every place a model's text was cut before other seats read it: stage, field, original and kept length; `[]` when nothing was cut), `disputes[].round` can be `"build"` (the builder's own DECLINED lines; a reply made only of them stops the run), `panelVerdicts[].no_answer` (`"no answer: thinking used the whole cap"`: an unheard seat whose reply was cut off at its cap after spending its tokens on thinking and carried no text; never a pass), `stages[].cappedAt` (the output cap a reply was asked at: the seat's own, or the bigger one a retry used) and `stages[].noAnswer` (the same mark on the stage). An advice call that an earlier version ran has `advise` (the council advisor's roll-up); nothing writes it any more.

Since 0.8.4 (the dissent record): `dissents` (top level; only when the run ended at the top layer's sign-off with an open objection of a lower-layer judge that the top layer overruled without closing it), `dispute.open_objections[].dissent` and the mark `dissent_on_record` in `ending.basis`.

Since 0.8.4 (additive; on every run that ends with a report): `ending_word`, one word for how the run ended (signed_off, signed_off_at_top_not_agreed, escalated_signoff, early_finish, rule_no_handler, finish_chosen, layer_stop, no_reviewer_heard, not_quorate, stalled or round_cap), and, for a finish chosen at a stop, `stop_kind` (the stop's kind, with `/<why>` when it has one). `final_read.run_end` is the reading before the final read (a final read that objects turns an agreed run into not agreed), and `ending` says how the top layer's sign-off ended; a signed_off run is agreed when it passed and no final read blocks it or when `ending` says agreed, an escalated_signoff or finish_chosen run only when `ending` says so, and every other word is never agreed. `dispute.reason` stays, a copy derived from the word in its older spelling (at a finish at once at the final-read stop, where the word is `finish_chosen`, it can still read `round_cap`). A run that waits at a stop has no report and no word.

Since 0.8.4 (additive; a chain with `handoff_contract.milestones`): `handoff_milestones.status_set_by_harness`, present only when the harness replaced the handoff's Status word (`ready_for_build` or `partial`) with `needs_decision` because the run did not agree and nobody had accepted the plan as it stands. `handoff_milestones.status` stays the word the seat wrote; HANDOFF.md carries `needs_decision` and a note line under it, and the stage file `handoff.md` keeps the seat's own text.

Since 0.8.4 (additive; written after the run ended): `acceptance`, present only when a person (`council accept`) or the handling session (step `accept` of `stop_decide`) accepted the plan of a run that ended without agreement, as it stands. It is derived from the gate ledger, which is the authority, and agrees with no judge: the ending word, the banner and the open objections stay. It names the gate, the actor and channel, the time, the reason, the open objections and the late findings still carried at the end accepted as they stand (a late finding is marked `late: true`; with the session's person test for each when the session accepted) and, when the harness had replaced the handoff's Status, the word the seat wrote. HANDOFF.md carries one line under its banner and the seat's own Status, and `handoff_text.file_sha256` follows the file while `file_sha256_at_end` stays the file as the run wrote it.

Since 0.8.4 (additive): `handoff_text.open_objections`, present only when the chain has a handoff stage and the run ended agreed on the handling session's build check with `passed` false and objections still open. It holds one row for each of those objections (`id`, `layer`, `severity`, `problem`; `layer` and `severity` can be null), as the handoff prompt listed them for its seat, and `council handoff --from-run` reads the rows back for its own prompt.

Since 0.8.4 (layer 1's revision limit sending the plan up to layer 2): the value `layer1_bound` in `escalations[].trigger` and `layers[].escalated_by`, and `escalations[].unresolved_at_bound`.

Since 0.8.4 (additive; on every run of a unanimous layered chain that reaches its end): `final_read` (the top-layer seats that had not read the plan as it ended read it once, and, with the sorting on and a run that ended without agreement, so does a seat that had read it but was not shown an objection or late finding opened or amended since its last sorting; `ran`, `run_end`, `final_sha` and one entry per asked seat, each with `read` and `reasked`, and either `meets` and `failures[]` (it read) or `why` (it did not)) and, only when the chain keeps `answer_back` and demands ratings: `final_read.seats[].sorting[]` (that seat's sorting of the open objections, each row an objection id sorted `must_do` or `may_leave` for the build, with its reason; a `must_do` that names no criterion and no decision carries `ungrounded: true`), `final_read.seats[].sorting_ignored` (how many of that seat's rows were ignored; present only above zero) and `final_read.sorting[]` (the seats' sortings combined, one row per id: `may_leave` only when every top-layer seat's closing word is may-leave, otherwise `must_do`; a seat that gave no word counts as must-do; `ungrounded` when no seat's `must_do` names a criterion or a decision). With the sorting on, a top-layer seat may also hand in a defect that no listed item names: it is kept in `final_read.seats[].sorting_new` and recorded as a late finding (`late_findings[].found` is `final_read`), and `final_read.reused` lists the top-layer seats that were not asked, with what they had said. A top-layer seat's verdict row in `panelVerdicts[]` may carry `sorting` and `sorting_ignored` on the same terms, and `sorting_new` (a defect the seat named only in its sorting; at the seat's last verdict it is also a late finding). Each row of that sorting may carry `reasons_shown_in`, the round in which the objection's raiser was first shown the seat's reason. For a late finding found at a seat's last verdict (`found` is `last_verdict`), `sorted` is that seat's own word, replaced by its later word at the final read, joined with the other seats' words. For one id `final_read.sorting` and `late_findings[].sorted` can differ: a late finding that no top-layer seat sorted must-do and that not every top-layer seat sorted may-leave has `sorted` null, while its row in `final_read.sorting` (when a seat sorted it) reads must_do. When every top-layer seat's closing word on an objection is may-leave (the seat's own sorting at the final read, or, for a seat that did not need to read, its sorting at its last verdict) and the objection is rated below 4 and was never rated 7 or above, the closing read closes it: its entry in `dispute.open_objections` gets `closed_by: "final_read"` and stays in the list, without its `dissent` mark. The readers of what is open at the run's end leave it out: the deliverable's Unresolved dissent block (written again from the entries still open), the label count, the builder tasks of an early finish, `argued` and `council handoff --from-run`, and the dissent record (`dissents`). At an agreed ending the handler's build check is asked after layer 3's last read of the run (its signing verdict, which is the final read there: no call is made and `final_read.ran` is false) and lists the late findings that verdict named; a not-agreed ending has no build check of its own, and its record follows the closing read. A `must_do` row of any of these sortings may also carry `route` (`writer` or `proposers`: where the seat says the fix belongs; a closing read only recommends it and sends nothing back), `route_asked` (`proposers`, when a seat asked for the proposers on a chain with no proposer seat; the route is then recorded as `writer`) and `route_unread` (what the seat wrote when it was neither). On a combined row and on `late_findings[].sorted`, `route` is `proposers` when any seat's must-do named it, otherwise `writer`. These appear only when the chain has the Decisions rule on. When a layer-3 seat's list of open objections and late findings is read in parts (the list does not fit one prompt), `final_read.seats[].parts_unread` lists the parts that could not be read, each with its call label and the cause (`label`, `why`; present only then); the objections and late findings in them have no word from that seat, and the combined sorting reads a seat that gave no word as must-do. A top-layer seat may attach a concern to its final read (`final_read.seats[].concern`): a note for the build to watch that does not claim that a criterion fails. It is listed in HANDOFF.md under Concerns and in the BOARD's final-read section, is never an objection or a late finding, has no rating and holds nothing back. An objection a top-layer seat raises at the final read carries its quote, an id like every objection (O- and eight hex digits; another text under the same id gets a suffix, #2) and not_debated: true. A defect the seat names in its sorting with a passage that is in the plan is such an objection, and a defect it cannot anchor in the plan is a late finding (late_findings[].found is final_read) with the seat's rating. `final_read.basis` (`final_read_objection`; present only when the run ended without agreement, the final read ran, and a top-layer seat asked at it objected with a failure rated 4 or above, a failure with no readable rating, or no failure named; the failures it named are in `seats[].failures[]`). `final_read.coverage_only` (`true`; present, with `reason` `finished_at_once`, only when every top-layer seat had already read exactly this plan and one more read was owed, because an objection or late finding was opened or amended since a seat's last sorting; that read was not made). `handler_notes` (the notes the handling session added to the build list with `council note-add` after the run ended: n, at, actor, text and, when it names one, the objection; present only when there is one; a note sorts nothing, and `handoff_text.file_sha256_at_end` keeps the hash of HANDOFF.md as the run wrote it, while `file_sha256` follows the file with its notes; BOARD.md is not re-rendered).

Since 0.8.4 (experimental and additive; only the last item below is read by a verdict): `producer.code_sha256`, a sha256 over the `.js`, `.mjs` and `.json` files under the folders `package.json` `files` lists (less its exclusions), as present on disk (two different stamps for one version mean the files differed, not two harness versions; absent in a packaged binary and wherever it cannot be computed), and `producer.sittings[]`, one entry per sitting that reached the chain (when, process, version, code stamp). A stopped run that is resumed keeps each earlier stop as `stop-0001.json`, `stop-0002.json`, ... in its run folder (the stop, what stopped the run and the small stop markers; not the partial report). One value is read by a verdict: the finding kind `names_prompt_only_section` in `handoff_milestones.findings[].kind` (a handoff that names a section title which neither it nor the plan has) keeps a recursive-planning node from counting as `ready_for_build`, like every other finding of that list.

Since 0.8.4 (experimental and additive): `delivered_text.summary_block`, present only when the handling session added a summary and index block at the top of `deliverable.md` after the run ended. In it, `chars` is the block's length as written (its closing `---` line included), `sha256` its hash and `text_sha256` the hash of the session's own text; a reader takes the first `chars` characters off only when their hash is that `sha256`. The block is not one of the `harness_notes`, and `delivered_text.sha256` and `body_sha256` stay the hashes of the file and the body the run wrote.

Since 0.8.4 (experimental and additive): `plan_checks`, present only when the run delivered a plan, holds what the two information checks of the plan's own body found, one entry per check that was asked for: `claim_markers` flags a statement about the project that carries none of the four markers (CHECKED, UNVERIFIED, DISPUTED, ABSENT), a DISPUTED marker no dispute pass wrote, and a CHECKED marker whose cited range or excerpt no seat was shown, and `test_identifiers` lists the names a fenced test file of the task uses that the plan never mentions. A check that ran has `ran: true` and its `findings` (an empty list means it ran and found nothing), a check that did not run has `ran: false` and `reason` `no_plan_body`, and a check that was not asked for has no entry, so an absent entry is not an empty one; a finding never changes `passed`, the exit code or any text.

Most optional stages add their field only when the chain turns that stage on. When the field is
missing, the stage did not run. It does not mean the stage found nothing.

## Read it defensively

- Some fields come from a model's own JSON reply, and the harness passes them through with little
  checking. The schema marks them "model-supplied". Examples: a proposal's `title`/`what`/`how`, a
  reply's `text`, the extra keys an `amend` reply brings. Check a field exists before you use it.
- `signoff[].lab` is the seat's lab (since 0.7.7). `signoff[].provider` holds the same value despite
  its name; it is deprecated and stays until a version 2. Read `lab ?? provider`.
- Since 0.8.4, a row of `signoff[]` or `panelVerdicts[]` with `cut: true` is the reply of a seat that had answered when the person's finish ended the run (AI-README says where). It counts for no sign-off and no read; its objections count as open (`signed_text.open_objections`), except one its raiser withdrew in a completed round of the exchange the finish cut, which is closed. Of the others, one the seat already held open before the finish keeps the row it had; any other is marked `cut_off`, and where the report carries a dispute record `dispute.open_objections[]` lists it with `cut_off: true` and `last_raised_round`.
- Since 0.8.4, an objection record (`lastCritique.failures[]`, `signoff[].objections[]` and `layer_debates[].objections[]`) carries `unanchored: true` when it quotes no passage of the plan. The flag says what the record holds (no quote is recorded); it does not say whether the judge was asked for one. A record that carries a quote has no such field.
- Since 0.8.4, `proposer_returns[]` (experimental) has one row for each objection of the top layer that said it was about a decision: the route taken (`proposers` or `writer`), the status (`ran`, `failed`, `no_proposers`, `refused`), the Decisions entry, how the objection was chosen and what each proposer wrote. It is absent unless the chain has the Decisions rule on. Three new stage labels, `return-alt-<round>-<lab>`, `return-post-<round>-<lab>` and `return-answer-<round>-<lab>`, are the proposers' calls.
- Since 0.8.4, `quote_attached_in` on an objection record (`lastCritique.failures[]`, `layer_debates[].objections[]`) names the stage whose reply carried its quote when the quote was not in the judge's own failure but was attached to it in the exchange (a raiser's reply, or its own post). The objection keeps the id it was raised with. An attached quote does not change `quote_status`: that mark describes the judge's own failure and stays as the quote check made it.
- Since 0.8.4, `quote_status` on an objection record can be `in_excerpt`, with `excerpt_id` (an `E-<n>` id in `excerpts.jsonl`): the quote is not in the task's fenced source but is in an excerpt of project text that the handling session added during the run. A run that recorded an excerpt has `excerpts: { count, file_sha256 }` in `report.json`; the lines are in `excerpts.jsonl` in the run folder (`schemas/excerpts-v1.json`). A line can carry `supersedes` (optional, since 0.8.4): the id of an earlier line that this line replaces, one recorded while the privacy switch was off that no call on the run's record had sent to a seat; the earlier line stays in the file and is no longer used.
- Since 0.8.4, an objection record (`lastCritique.failures[]`) carries `spans` when it quotes anything: one entry `{ text, located_in }` per quoted span (its `quote`, the quoted passages of its problem and its fix, and those of the evidence of the judge's FAILED table row of the same criterion), each once and at least 8 characters once normalised. `located_in` is the first of `draft`, `fenced_source`, `excerpt`, `request` and `criteria` that holds the span, or null when none does. The comparison ignores case, emphasis and quote marks, so it is looser than `quote_status`, which is case-sensitive. The marks are a record: no objection is dropped or gated by them, and the objection id does not read them. An objection adopted at a stall ruling keeps the marks its raiser's copy had; one adopted through a ruling given in a layer's ordinary review carries none.
- Since 0.8.4, a `sustained` row of `answer_back_replies` carries `spans` too when the judge's evidence quotes anything: the same `{ text, located_in }` entries, marked the same way, for the passages the judge gave for keeping its objection. A record only: the objection stays open as before, and a withdrawal is decided as before (a quoted passage found in the shown draft, or in a peer's evidence the judge was shown). A passage the judge quoted from the writer's reason, or from a peer's evidence, reads null.
- `alternatives.dropouts[].reason_code` (since 0.7.7) matches the spelling in `signoff[]` and
  `panelVerdicts[]`; `reasonCode` is its deprecated alias.
- `signoff[].passed` means the seat *stated a pass*: it declined to give a verdict. It is not the
  run's top-level `passed`.
- A `stages[]` entry with `priced: false` shows `usd: 0`, which means *unknown*, not free. Check
  `totals.unpriced` too.
- `totals.usd` is the sum of the stages' settled `usd`. It excludes an unsettled reservation (a call that was sent when the process ended and never settled): `council --spend`, `run_status` and a resume's cap count
  such a reservation at its worst case (once, at the larger of the two when a usage file also carries its id), and a settled call whose usage file was never written (its `reserved` line is in the folder), so those figures can be higher than the report's total; `totals.counted` holds the count-once figure.
- Since 0.8.4 `totals.usd` also counts the cost of paid stage files that no `stages[]` row accounts for (a label an earlier sitting paid for and the finishing sitting never asked again, for example after the chain
  gave its criteria in place of a criteria seat): that cost is shown separately as `totals.unreplayedUsd`, and the files are listed in `unreplayed[]` (experimental, present only when there were any) as `{ label, usd, reservationId }` each.
  A report written before 0.8.4 does not count them; `council --spend` and `run_status` add them when they read such a report.
- Since 0.8.4 `totals.providerReported` (experimental, present only when the run folder holds a paid OpenRouter record) shows what the provider REPORTED beside THC's own count: `{ cost, attempts, thcUsd, attemptsWithout, unverified: true }`. `cost` is the sum of the figures the provider reported for the `attempts`
that carried one (the provider documents it as "cost in credits"; the unit is not verified), `thcUsd` is THC's own usd for exactly those attempts, and `attemptsWithout` counts paid normal replies that carried none (a file from before 0.8.4 reads so). It is derived from the run folder and counted in no total;
failed attempts, which carry no figure by design, are not in `attemptsWithout`. `council --spend` and the MCP `spend_report` show the same object per run; it is equal to this one when the report is written, and a one-call record written later (`handoff --from-run`, `digest`) is counted by them and not by this file, as with `totals.usd`. An exception is a capped `--rematch` or `--replay`, whose `report-partial.json` is written without this field.
- Since 0.8.4 `totals.counted` (experimental, present only when the run folder holds a paid record) is the count-once figure of the folder: `{ usd, estimatedUsd, bases, unlabelledUsd?, unknownFigures? }`. `usd` counts every paid record once (the usage files, the superseded and charge files, an unsettled reservation at its worst case, and a settled call whose usage file was never written and whose `reserved` line is in the folder), so it can be higher than `totals.usd`, whose meaning is unchanged. `estimatedUsd` is the part that is an estimate (a typical cost, an expected cost of a retry, a reservation or an attempt at its worst case); `bases` is the amount per `basis` (`token_priced`, `provider_usage`, `typical_error`, `expected_retry`, `reserved_unsettled`, `worst_case`). Records from before 0.8.4 name no basis and are in `unlabelledUsd`. An unsettled reservation beside a usage file that carries its id counts once, at the larger of the reservation's worst case and the file's amount. A settled line with no `reserved` line is damage to the file: it is counted nowhere, and `council --spend` names it. `totals.counted` is THC's own count, never the provider's bill; `totals.providerReported` stays beside it and in no total.
- Since 0.8.4 a `stages[]` row also carries `basis` (experimental, optional): what its `usd` stands for, `token_priced` (THC's own count of the reply) or `worst_case` (the reply's usage could not be read, so one attempt's worst case was counted). It is absent on a $0 stage and on a report from before 0.8.4. `council --spend` shows a total's estimated part (`(of which $x estimated) of that total`) when part of a figure is an estimate; the answer of the MCP `spend_report` does not carry it (it has no `estimatedUsd` and no `totalEstimatedUsd`).
- Since 0.8.4 a stage's usage (`<label>.usage.json`, and the usage of a `stages[]` row) can carry `cacheRead` and `cacheWrite` (prompt tokens read from, and written to, a provider's prompt cache; a count the response did not carry is absent, never 0), `cacheAsked` (`"5m"` or `"1h"`: the call carried a cache marker) and `cacheCounts`. `cacheCounts` is `"unknown"`, `"write-not-reported"` or `"write-in-input"` on a call that was billed a cache write the response does not state, or whose charge departs from the write count it reports: `"unknown"` when the response carried no cache counts, `"write-not-reported"` when it carried a read count and no write count, and `"write-in-input"` when it carried a write count (a zero included) that did not set the price: THC counts a written token as lying inside the prompt (checked against the replies of one paid test only, for one model on one host) and charges every prompt token that was not read from the cache as a write. THC charges such a call a cache write on the part of its prompt that was not read from the cache; for `"unknown"` that is the whole prompt, and the cap errs high. `usage.input` leaves out the tokens read from the cache, and `totals.input` is the sum of the stages' `usage.input` less the `cacheWrite` of the calls whose `cacheCounts` is `"write-in-input"`, each such call taking off at most its own `usage.input` (a call to another OpenAI-compatible model that reports a write count keeps it inside `usage.input` and `totals.input`). `totals.cacheRead` and `totals.cacheWrite` add up the counts the responses carried and appear when a call that used a cache carried the count, a zero included (a call used a cache when it carried a cache marker or a count above zero, or was billed a cache write its response does not state, `cacheCounts` `"unknown"` or `"write-not-reported"`; `"write-in-input"` alone does not make a call one that used a cache); `totals.cacheNotReported` lists `"read"`, `"write"` or both when a call that used a prompt cache left that count out. A count not named in `cacheNotReported` was carried by every call that used a cache, and a count that no such call carried is absent from the totals.
- Since 0.8.3 a `stages[]` entry that was paid for by a call carries `reservationId` (r1, r2...): the id of the spend reservation written before that call was sent, so a charge is matched to its reservation
  by id and not by label (a label can be run twice). A mock stage, or a call projected at $0, has none. A stage replayed from disk carries the id of the sitting that paid. `superseded[]` (experimental, present only when a
  stage was set aside and paid for again) lists the records `totals.supersededUsd` absorbed: `{ label, usd, reservationId }` each (a charge record adds `kind`, `waste` or `billed`).
- Since 0.8.3 a run whose plan holds a block marked `the-high-council:tree-split` carries `split_contract` (experimental): `{ sha256, valid, findings[] }`, the result of the $0 checks on that block
  (`sha256` is of the block as canonical JSON, null when it does not parse; each finding is `{ check, rule, message }`). It never changes `passed`.
- Since 0.8.3 a run that is a member of a recursive-councils tree carries `tree` (experimental): `{ treeId, node, generation, attempt, parentNode, depth, splitSha256, bundleSha256 }`, copied unchanged from the `tree` field
  of its `run.json` (`treeId` is the run id of the tree's root run; `node` is a path of milestone ids such as `R/M2`). A run that is no tree member has no `tree` key.
- Since 0.8.3 a run with a session-seat stage (`provider: external`) carries `roster_answers` (experimental): `{ design_companies, recorded_companies, unverified_seats, seats[], note }`, who answered those seats AS DECLARED by the MCP client and the session, never verified, and the review panel's company count as recorded next to the count the chain was designed for. Each `seats[]` entry is `{ label, seat_lab, asked_for, answered_by, company, status, panel }`. The stage rows gain `asked_for` (the model the seat asks for, or `claude-code-session` when it asks for none) and `answered_by` (`{ client: { name, version } | null, model | null, declared_by }`; absent when the answer was written as a file). It changes no stage, cost, approval or `outcome`; a seat answered by another model is not a dropout.
- Since 0.8.4 a stage row has four more fields (experimental; null where there is nothing to say, and absent on a row recorded without them: a stage file from before 0.8.4): `persona` (the persona the row's seat is configured with: a judge's `persona`, a bare name, or a debating seat's `role.persona`, a key into the persona set), `persona_name` (the name the call's prompt actually carried, noted when the prompt was built; `null` when it carried none, for example a judge's persona while `seat_personas` is off), `persona_set_sha256` (on a debate row: the SHA-256 of the persona set that prompt was built from, so a persona file edited later does not change it; `null` elsewhere, a judge row included, because a judge's name is never looked up in the set) and `model_source` (where the row's `model` comes from: `provider`, the id the seat was seated with, not checked against the reply; `declared`, a session seat's answerer named a model; `undeclared`, it named none). A run whose debate prompts were built from the persona set also has `personas_source` (`default`, `file` or `fallback`), `personas_sha256` (the SHA-256 of the canonical JSON of that set) and `personas_used` (the keys, in seat order); the first two are `null` when the rows name different sets, and each row's own `persona_set_sha256` is then the record. For a session seat the set is the one its pause wrote down, not the file as it is when the answer arrives.
- `task` is never absolute (since 0.7.7): it is relative to the directory the run was started in,
  or the file name alone if the task lives outside it. Reports from 0.7.6 and earlier can carry an
  absolute path after a resume, rematch, replay or `init`. `task_sha256` (experimental) is the
  SHA-256 of the task text, so a reader can match a report to its task file without the path. The
  path still names a file on the author's disk; consider dropping it before you publish a run.
- `fromRun` follows the same rule since 0.7.7: relative to the start directory, or the run
  folder's name alone.

## A run the spend cap stopped (`report-partial.json`)

A run that stops early writes no `report.json`: that file existing means the run finished. Since
0.7.7, a run the per-run spend cap stopped writes `report-partial.json` next to
`STOPPED-budget.json` instead, so a run capped after many rounds can still be read as data. It is
the same schema, built by the same function from what the run had when it stopped, with three
experimental fields added:

- `partial`: always `true`. It never appears in `report.json`.
- `stoppedBy`: `"budget"` (the per-run spend cap, exit 4). A record that an earlier version wrote for an advice call can also say `"user"`, `"client_cancel"` or `"wall_clock"`. A reader must ignore a value it does not know.
- `stoppedAtStage`: the label of the stage the run stopped before. That stage was never paid for.

Read it knowing the run did not finish:

- A stage the run never reached has the value that means "did not run": `null`, `[]`, `false`,
  or the field is absent. `passed`, `outcome` and `signoff` describe the state at the stop. They
  are not a verdict.
- `stages`, `totals`, `proposals`, `debate` and `panelVerdicts` (one row per seat per review round)
  hold everything that did happen, up to the stop.
- `finished_at` is when the run stopped. The privacy rules are the same as for `report.json`:
  `task` and `fromRun` are never absolute.
- `BOARD-partial.md` is the same board for people, headed as a stopped run's. It is written once
  the run has got far enough to have a board.
- A `--resume` deletes both files together with `STOPPED-budget.json`, because they describe the
  run as it stood at that stop. If the resumed run finishes, it writes `report.json`. If the cap
  stops it again, it writes fresh partial files. A capped `--rematch` or `--replay` folder gets
  them too.

### A layered run stopped at an overseer limit (0.8.3) or at a stall that cannot be passed up (0.8.4)

A layered run that uses all its overseer rounds, or whose layer 1 needs more revisions than it is allowed (when layer 2 has used its revisions and objects again, the plan goes up to layer 3 instead, while a pass is left), or in which an objection stood unchanged and could not be passed up (the top layer holds it; no pass is left; the chain keeps no answer-back list or does not ask its judges to rate; or the next pass is a ladder pass, which does not pass a plan up), exits 23 and writes the same partial files (`stoppedBy` is `overseer_cap`, `layer_bound` or `stall_stop`), plus a `stop` block in `report-partial.json` and `deliverable-partial.md`: the plan as it stands, without the declined lines. The run is resumable and not agreed. If the person ends it with `--finish`, `report.json` is written with `passed: false` and the same `stop` block, now with `chosen: "finish"`. A layered run that has no handling session and is not made only of mock seats does not stop at the overseer-round limit (when it is not the hard stop after seven rounds) or at a silent seat of layer 1 or 2: nobody could choose there, so it ends there after the final read, not agreed, with `chosen: "rule"` in the `stop` block and `rule_no_handler` as `dispute.reason`. Such a chain is refused at the CLI and the MCP start, so only a program that calls the harness directly reaches this. If `report-partial.json` is damaged or missing, a plain `--resume` rebuilds the partial files from the stages already on disk (a stage file you removed is asked of its seat again, within your limit) before the choice can be given. A run paused at a credential-shaped string in a prompt (exit 11) whose person gave `--finish` and then `--continue` ends without those partial files: `report.json` is written with `passed: false` and a `stop` block with `kind` `secret_pause`, `chosen: "finish"` and the stage as `label`, on any chain, layered or not. A layered run with unanimous sign-off that stopped at the spending limit inside the review rounds and was given `--finish` (exit 4, recorded, nothing run) ends after the person's raise with `report.json` `passed: false` and a `stop` block with `kind` `budget_stop`, `chosen: "finish"`, the stage the limit stopped as `label` and, when per-provider caps are armed, `cap_name`; the final read of the top layer ran first. `stop.reviewed` says how much of the pass the review ended in was asked (`none`, `part`, `all` or `signed`); on a layered chain `asked_layers`, `cut_layers` and `not_asked_layers` name the layers, a layer that was cut off is `unfinished` in `layers` and its seats' rows in `panelVerdicts` and `signoff` carry `cut: true`, and one never reached stays `not_asked`. A `stall_stop` `stop` carries `why` (`top_layer`: the top layer holds one of the stalled objections; `last_pass`: it holds none and no pass is left; `climb_not_shown`: a pass is left, but the chain keeps no answer-back list or does not ask its judges to rate; `ladder_next`: the next pass is a ladder pass, which does not pass a plan up), `top_layer`, `pass_left`, and `stalled` (the objections that stood unchanged and the passes they stood in); `rounds` is there on a chain with overseer rounds, and `overseer_round` is 0 on a chain without them. A top-layer stall at the overseer-round cap is the cap's own stop (`overseer_cap`) and carries `stalled` too. From seven used overseer rounds (`rounds` 7 or more) the stop is the hard stop: `--continue`, `--finish` and revising outside the Council are all offered.

Since 0.8.4, a run whose plan was passed up a layer (by a stall, or at layer 2's revision limit) before it stopped carries `escalations` in `report-partial.json` too. In each row's `outcome`, an `overruled` objection is closed when its row has `stays_open` false and stays open when it is true (a row without `stays_open`, from a report written before 0.8.4, reads as closed), an `undecided` one still stands as the objection of the judge who raised it, and a `sustained` one lives on under the ids in `adopted_as`, which `lastCritique.failures` lists with `sustained_from`. A partial has no `dispute` block, so read the standing objections from `outcome`.

An advice call that an earlier version ran carries an experimental `advise` object in its `report.json`; nothing in THC writes it any more, and `schemas/report-v1.json` no longer describes it (0.8.4).

## Checking a run folder

```js
import Ajv2020 from 'ajv/dist/2020.js';
const ajv = new Ajv2020({ allowUnionTypes: true });
ajv.addKeyword({ keyword: 'x-stability', schemaType: 'string' });
const validate = ajv.compile(schemaJson);   // schemas/report-v1.json
validate(reportJson) || console.error(validate.errors);
```

`test/report-schema.test.js` does the same against real offline runs of the shipped mock chains
that finish in one sitting (15 of the 18; the other three pause for a person or stop at their cap),
a resumed `mock-external` run, a descending-mode run, and one run with every optional stage turned
on. `test/report-partial.test.js` validates the `report-partial.json` of capped `mock-budget`,
multi-round, descending, `--rematch` and `--replay` runs against the same schema.
