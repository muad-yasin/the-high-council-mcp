The High Council · Skills

You can build anything in a weekend.
So can everyone else.

What decides the outcome now is the part most people skip: deciding what is worth building, and proving it actually works. These skills write that part down, so your AI coding agent does it too.

Free and MIT-licensed. They work in any Claude Code project, with or without The High Council harness. No account, no API key, nothing to install beyond copying folders.

No efficacy claim. Nothing here has been measured against working without these skills, so we don't say they make results better. Every rule says what it guards against and why - most began as a real failure on a real project - so you can judge each one yourself.
What a skill is

Rules your agent loads only when they apply

A skill is a folder with a SKILL.md file: a focused set of rules, checklists, and a list of mistakes to flag. Claude Code reads the short description of every installed skill and loads a skill's full rules only when a task matches it. Deeper material sits in a references/ folder that is opened only when needed, so a large collection costs little until it's used.

The rules are concrete on purpose. Not "be careful with migrations," but "Golden fixtures prove compatibility; a careful read-through does not. Freeze one real example per meaningful state at the current version and load each in a test."

Core agentic work

For any task an agent takes on

Skills for the work around the work: defining it, sourcing it, checking it, carrying it across sessions and agents, acting on the world safely, operating a screen through a computer-use tool, writing the files an agent loads, vetting someone else's skill before it is loaded, and running the session that is in charge of other sessions. They apply to coding and non-coding tasks alike, and to setups where several models propose, critique, and hand work to each other.

task-scoping

Starting a multi-step or unclear task, delegating, starting an unattended run, or deciding whether something is really done.

Guards against
  • Acting before "done" and a stop condition are written down
  • Silent assumptions; questions asked without a stated default
  • A default recorded as the requester's decision
  • Risky, irreversible steps discovered only when reached
  • Partial results reported as if they closed the whole problem

research-and-sourcing

Any claim about the outside world: APIs, versions, prices, studies, real people and companies.

Guards against
  • A search summary mistaken for having read the source
  • Two copies of one press release counted as corroboration
  • An inference quietly hardening into a "fact"
  • Numbers stripped of the benchmark and date they belong to

verification-and-critique

Before reporting anything done, when reviewing any output, when answering a review's findings, when designing a review, vote, or debate.

Guards against
  • Self-review treated as proof; logs trusted over artifacts
  • Tests edited in the same change that makes them pass
  • Unreadable or missing verdicts counted as passes
  • An empty result read as clean; a finding that blocks without being demonstrated
  • Debate where agreement flips a correct answer to a wrong one

context-and-handoff

Long or multi-session work, delegation, pausing and resuming, writing or relying on an instruction file, several agents sharing one workspace.

Guards against
  • Quality decay from overloaded context
  • State that lives only in a conversation that will be lost
  • A stale document followed against the code
  • Vague briefs and handoffs that hide what already failed
  • A peer agent's word treated as the owner's approval

tool-and-action-discipline

Any action that changes state, spends money, or is visible to others; loading a third-party skill or plugin - and designing tools for agents.

Guards against
  • Destructive commands aimed at a pattern instead of a confirmed list
  • Spending checked after the call instead of before it
  • Instructions smuggled in through tool output or fetched pages
  • Third-party skills and plugins loaded unread
  • Human approval gates skipped, faked, or routed around

computer-use-discipline

An agent operating a desktop, its apps or web pages through a computer-use tool: clicking, typing, reading the screen.

Guards against
  • The tool's "OK" taken for what the application did
  • A click or a submit repeated after a timeout
  • Text on the screen followed as an instruction
  • Purchases, sends and consent prompts clicked without the person's confirmation
  • A screenshot offered as proof of a save or a send

agent-instruction-writing

Writing or changing a skill, wording or ordering the rules of a CLAUDE.md, an AGENTS.md or a rules file, or when an agent keeps missing a written rule.

Guards against
  • A rule left to wording when it needed enforcement
  • A description that does not say when to load the skill
  • The rule that matters most at the end of a long file
  • "Unless it matters" and other soft exceptions
  • Rules nobody dares delete because their reason is gone

skill-and-plugin-vetting

Before installing someone else's skill or plugin, before starting an agent in a cloned repository that carries agent files, and before taking an update.

Guards against
  • A skill or plugin loaded unread
  • A review of the files a skill names, not the files it contains
  • Compiled files accepted beside readable source
  • A scanner's pass reported as "safe"
  • An update taken without reading the difference

command-and-control

When a session is put in charge of other sessions: dispatching work, reviewing finished units, speaking to the owner, and getting a release done.

Guards against
  • The coordinator doing the dispatched work itself
  • A review of every step, and reviews nobody asked for
  • "Your rule" said of the session's own reading
  • Decisions for the owner buried in status text
  • The strongest model on a job a cheaper one does
Building software

For the code, the screens, and how they look

Five engineering and design skills that work across stacks - web, mobile, desktop, game UI, command-line tools - because they target failure classes, not frameworks.

backend-developer

Server logic, CLIs, data models, storage and migrations, background jobs, integrations, data scripts, generators.

Guards against
  • Errors swallowed so code looks like it works while doing nothing
  • Events fired before the state they describe is saved
  • Authorization left to the client; dependencies nobody checked exist
  • "Ran successfully" with no output artifact actually checked

test-suite-discipline

Writing or reviewing a change's tests, a suite grown slow or noisy, a test about to be deleted, skipped or pinned to exact wording, and the rule for what runs when.

Guards against
  • Tests that turn red on every intended change and catch no defect
  • Skipped and quarantined tests with no way back
  • A run of some tests reported as "the tests pass"
  • No named point at which the whole suite runs

frontend-developer

Anything that renders or reacts to input, down to wiring one button or showing one number.

Guards against
  • Screens that only work once there is already data in them
  • Text overflowing fixed boxes; layouts correct at one screen size only
  • Controls a keyboard or screen reader cannot use
  • Design mockups reproduced by eye instead of by their real values
  • Command-line errors that exit with success; output only a person can parse

ux-design

Before building any user-facing surface - including "just add a button."

Guards against
  • Visual design before the user's path is mapped
  • Missing empty, locked, loading, and error states
  • A destructive action with no undo and no question first
  • Notifications louder than the information deserves
  • Manipulative patterns shipped because they were profitable

visual-craft

When flow and implementation are right and the question is whether it actually looks right.

Guards against
  • A generic default look arriving unexamined
  • Contrast and colorblind safety judged by eye
  • One screenshot at one size trusted as proof
  • A vision model's opinion treated as a taste verdict
Game development

For games, engines and the assets that feed them

Five skills for work that runs inside a game engine or feeds one. They carry the same failure-class thinking as the rest, with neutral facts about the common engines and Blender, each dated and graded where it rests on documentation.

proof-discipline

Before a measured result gates a milestone, sets a baseline or decides a rebuild.

Guards against
  • A bar moved after the data was seen
  • A sample picked from what fails, then called representative
  • A test that could only ever say yes
  • The aggregate reported while a neighbouring case got worse

game-verification

Deciding whether a game change works, and whether a build may go to a person.

Guards against
  • A feature handed over that never ran in the integrated build
  • A skipped smoke test read as a pass
  • Screenshots from a run with no rendering
  • Timings taken on the wrong machine

open-world-streaming

Streaming, level of detail, collision loading and hitches in large worlds on weak hardware.

Guards against
  • Two coordinate frames compared with no conversion
  • A counter reading zero accepted as a clean result
  • Collision arriving after the vehicle
  • Budgets set from a faster machine than the weakest target

engine-editor-driving

An agent operating a game-engine editor over a bridge.

Guards against
  • A success reply accepted with no read-back
  • Object ids carried across a reload
  • Play-mode edits leaking into the asset
  • A timed-out call re-issued without checking whether it landed

dcc-agent-authoring

Driving Blender from an agent to build and export engine-ready assets.

Guards against
  • Interactive edits nobody can repeat
  • Scale and unit lost between export and import
  • A builder that grades its own output
  • A bridge server pinned by command name instead of source
Writing

For words people will read

Four skills that hand off in a fixed order - facts, draft, edit, independent read - plus one register for writing warmly about someone real. They cover marketing copy, documentation, announcements, articles and in-product text alike. The legal notes in fact-checking are general information, not legal advice.

fact-checking

Before drafting from real events, before publishing any claim about a real person or organization, and when a published claim turns out wrong.

Guards against
  • Quotes nobody said, or said less sharply
  • Figures and rulings never traced to the original document
  • False claims inherited from an earlier draft
  • A charge written up as a conviction
  • A published error fixed silently
  • AI-written text published with no disclosure where the law asks for it

drafting

Writing any new text, from a landing page to a help page.

Guards against
  • Filler written to fill a length
  • A piece that shows how something happened but never says why it matters
  • Endings that explain instead of land
  • A headline and first sentence that say the same thing twice
  • A status report that says yes about a check that could only say yes
  • A change note that praises the change instead of stating it

line-editing

Revising text that reads flat, generic, or machine-written.

Guards against
  • Polishing sentences in a piece with nothing to say
  • Machine-writing tells - named, with the evidence and its limits
  • AI detectors treated as proof about a person's work
  • Library-wide rewrites made before anything was graded

final-read

After editing, before anyone else sees the work.

Guards against
  • Claims "checked" from memory instead of searched again
  • A reviewer who quietly rewrites the piece
  • "Is this good?" answered yes by the author
  • Untraced quotes let through because a name was changed
  • A self-run read passed off as an independent one

good-news-writing

Warm, positive coverage of a real person or organization doing something good.

Guards against
  • Praise that reads like a press release
  • A villain invented to make the good deed look bigger
  • Backhanded compliments and untraceable quotes
  • Overstating a true, modest act

How they are written

Why the rules look the way they do

Keep the scar, drop the coordinates

Each rule keeps the failure that produced it and the reasoning behind it. Project names, file paths, and tool trivia are removed.

Structure over good intentions

A checklist, a gate, a second reviewer, or a hard cap beats "be careful." A mistake that happened twice gets a mechanical guard.

Evidence, graded

Where a rule rests on published research, the finding is paraphrased with its strength stated. Practitioner reports and inference are labeled as such.

Judgment ages well

Syntax gets automated first. Deciding what is true, what is good, and what is safe to ship is the part these skills focus on.

Delete what stops being true

Many rules encode something models currently do badly. When that changes, the rule goes.

One rule, one owner

Each skill says what it is not for and points to the skill that is. Where two skills need the same rule, one owns it and the other points to it, so copies don't drift apart.

Install

Copy the folders you want

Each skill is self-contained. Copy any of them into your project's .claude/skills/ directory, or into ~/.claude/skills/ to use them in every project. They follow the open Agent Skills format, so other agent tools that read SKILL.md folders can load them too.

git clone https://github.com/muad-yasin/the-high-council-mcp
cp -r the-high-council-mcp/skills/task-scoping your-project/.claude/skills/
cp -r the-high-council-mcp/skills/verification-and-critique your-project/.claude/skills/

Or install all of them as a Claude Code plugin; plugin skills are namespaced, for example /the-high-council:task-scoping. The plugin also registers The High Council MCP server, which does nothing until one of its tools is called.

claude plugin marketplace add muad-yasin/the-high-council-mcp
claude plugin install the-high-council@the-high-council

The catalog in skills/README.md lists every skill with when to use it. Changes are recorded in the repository's CHANGELOG.md; this page and the catalog are checked by the test suite against the real skills/ folder, so they can't list a skill that doesn't exist or miss one that does.
